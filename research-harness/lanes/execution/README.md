## 筛选与取样

从官方仓库及维护者页面出发，逐项检查是否承担 agent 的执行、审批、恢复或执行反馈。至少需要一个能定位到函数或控制流的证据和一份独立的日期/版本记录。产品选择时刻意保留最小实现与治理较丰富的实现，也保留具有相似组织来源的不同架构作对照。E02 与 E11 归同一项目家族；E04 用于校准基线；E10 是邻接的运行时而非完整 coding agent。案例数不代表独立厂商数、市场份额或 SOTA 排名。未涵盖无法验证的闭源内部实现。与仅有模型成绩的比较分开。

| ID | 选择原因 | 复核切面 |
|---|---|---|
| E01 | 风险阈值与会话事件 | 策略类与会话启用条件，错误推导为“默认总是开启”的反例 |
| E02 | 可配置多轮筛选器 | 尝试、评审预算、最终选取与独立验收 |

## 复算和扩展

1. 从每个 cases 条目的来源表定位 GitHub blob 固定 SHA，取 download_url 原始字节；将 Git blob 对象摘要与对应提交的 git tree 比对，随后保存本地 SHA-256。若更新，使用新 SHA 或内容哈希目录，保留旧字节。
2. 在同一仓库官方 Releases Atom 里定位该条目的 URL、标题、updated 与正文。一个快照含近十条发布，分析只使用被点名的条目。Atom 会滚动，旧日期复算优先读取已存快照。报告、网页正文同样计算摘要；OpenAI 内部实践的抓取边界为带定位的摘录。
3. 修改作者核对后的 notes.txt，运行 compile.py，按 case 生成同一事实数据源；capture.py 针对已有 sources.json 以只读方式校验所有快照。编译脚本将具体函数、测试及章节补入来源表。跨项目引用采用稳定 ID。
4. 从本目录运行 python probe_langgraph.py 验证同进程四种中断条件，分别与本机 0.2.71 的 probe-langgraph.json、独立安装 1.2.24 的 probe-langgraph-1.2.24.json 比对。两版四种条件一致，共八次。没有模拟云产品账号；供应商参考实现里的测试只作为静态证据。实验环境、版本及范围以输出为准。
5. 新快照可依照每个 source 的 download_url 独立下载；对于已迁移网页或不同内容，存新 hash，记录差异，不以更新的正文覆盖旧数据。source 的 date 与 retrieved_utc 分开。

## 已知局限

所选实现体现参考代码当前行为；企业托管端的配置、规模、组织权限与运行成本须分别在租户中核实。跨版本比较只在 release、dated changelog 或明示版本的材料下成立。E07、E06 在文档与源码不一致时保留了适用条件，没有把差异静默择一。
