# 交付链样本的筛查与复核

基线为 2026-11-20（上海）。围绕有明确输入、可观测状态和可中止或验收边界的问题进行目的抽样。先按作业接入、运行控制、持久等待、策略校验、代码审查、依赖合并、基础设施变更、部署同步和生产效果验证建立覆盖矩阵，再为每种机制寻找发布方源码与说明。该样本不能代表市场份额，也不是每一类产品的完整名单。

| 筛查决定 | 对象及理由 |
|---|---|
| 纳入 11 项 | 输入、执行或判定、交给人处理的边界可定位，并有可核对的公开版本记录。GitHub Actions Runner 与 Buildkite Agent 分别用于讨论宿主前后钩子与取消传播，不把相似的执行代理自动算成不同能力。 |
| 机制拆分 | Argo CD 观察期望与现场的差异；Argo Rollouts 使用时序指标控制推广。二者对应不同反馈对象，各自有单独仓库、控制器、版本和边界。 |
| 组件边界 | Jenkins 只考察 Pipeline Input Step，Temporal 只考察 Python SDK 的事件/回放语义，Buildkite 只核对公开 Agent，不能借局部源码推断托管调度。 |
| 暂未纳入 | GitLab Runner 与已选 runner 的执行职责重合。Dagger 的构建图和缓存是后续方向，本轮优先保留审批、补偿和异常处置。Mergify 的合并队列可补商业产品对照，本轮交付链先读可复查源码。 |
| 名称复核 | PR-Agent 仓库已从 qodo-ai 重定向到 The-PR-Agent，收录社区项目。对 CodeRabbit 等托管产品单独考察，避免用开源代码代证专有实现。 |

## Ingest / Query / Lint

1. 进入本目录，运行 `python fetch.py`（可加仓库短名）；`python fetch_release.py` 固化选定版本。前者取 GitHub 的官方 commit Atom feed，按截止日选择基线提交并下载固定 SHA 的文件与 release feed；后者抓取具体版本页面。GitHub REST 匿名配额不足不影响复算。首次抓取只在内容哈希对应的文件缺失时写新文件。如在未来重建历史，直接使用 manifest 的原 URL、已固定 SHA 与原始快照，时间切片已落出短期 feed 时从现有快照查询。
2. `cases.json` 提供中文事实、研究推断和待验证实验；每项两个源码/文档定位、一个具体版本定位。源码日期指抽样时所固定提交的日期（不代表文件引入日期），发布页面取 release 日期 UTC，另保留 feed updated 字段。已发现 Atlantis 等项目的页面发布日期与 feed 后续编辑日期不同，因此没有把 feed 更新日当发布日期。
3. `python compile.py` 用同一组陈述生成案例并复核每个 manifest 路径的 SHA256。发布原文和提交索引也在 manifest 中保存；复核时可按具体版本和所列函数定位，而无需重新搜索。
4. `python experiment_conftest.py` 下载对应官方 Windows x86_64 二进制、核对该版本 checksum 后，用临时文件执行三组 JSON 输入。`python experiment_pragent.py` 用固定 SHA 源码在本地直接调用仓库配置作用域函数。实验原始记录在 `experiment/`。这些实验均未接入生产服务、客户代码或账户。

## 复核结果和遗留问题

11 个产品/项目，每项 3 个正文引用。另存 22 份索引供历史校验，共 55 份原始材料。所有原始字节的 SHA256 在生成案例时校验通过。1 项 CLI 层实测，1 项配置函数层实测，另外 9 项未运行。所有产品的跨团队采纳率、净节省工时与线上安全性都没有通过现场数据验证。重要反例已写回案例，包括 Argo Rollouts 候选版本、审批与计划摘要的关系、Temporal 保留旧有执行历史、文档描述与中止后实际完成之间的差异。
