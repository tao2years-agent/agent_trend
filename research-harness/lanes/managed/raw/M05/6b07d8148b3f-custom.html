Custom checks

Define your own validation logic using natural language instructions for pre-merge checks.

How Custom Checks Work

Custom checks run in a secure, read-only environment against your PR. The agent has access to:
  • Changed files, code snippets, and relevant git history
  • PR title, description, linked issues, and review discussion
  • CodeRabbit’s posted review comments, with severity and resolution status (see Gate on CodeRabbit review comments)
  • Pattern and code search tools (ast-grep, ripgrep)
  • Sandboxed shell commands to inspect the repo
  • Web lookups for public documentation
  • Connected MCP tools for internal systems
Process:
1

Analyze

CodeRabbit interprets your instructions against the PR context
2

Verify

The agent gathers evidence using available tools to substantiate findings
3

Decide

Emits Passed, Failed, or Inconclusive with reasoning

Inspecting linked repositories

Custom checks can inspect committed files in linked repositories that CodeRabbit has authorized for the current repository and your plan. This is read-only file inspection; custom checks do not run the linked repository’s tests or build. Checks that run automatically during a review reuse the linked repositories and refs selected for that review. When you use run pre-merge checks or evaluate custom pre-merge check, CodeRabbit resolves linked-repository access and refs again. If an explicit branch or pull request reference in the PR description cannot be resolved, that linked repository is unavailable to the check instead of silently falling back to another branch. A check that requires this evidence returns Inconclusive and explains what is missing.

Gate on CodeRabbit review comments

A custom check can read the review comments CodeRabbit has already posted on the PR. Use this to block a merge only on serious findings that are still open, for example Critical and Major comments without a confirmed fix, instead of on every comment. For each review thread that CodeRabbit started, the check receives the first comment, including its severity badge (Critical, Major, Minor, Trivial, or Info), the file and line, a note if that location is outdated, and two statuses:
StatusValuesMeaning
discussionresolved, unresolved, unknownWhether the thread is resolved in your Git provider.
codeaddressed, unconfirmed, unknownWhether CodeRabbit’s last automatic check of the thread confirmed that the code was fixed. unconfirmed means the check did not confirm a fix; unknown means no check result is available. This is the last recorded assessment, so it can predate the current code.
Automatic runs after a review also receive the new findings from that review, with their severity. These findings are not posted yet, so they have no discussion or code status, and the check treats them as outstanding. If your instructions only ask about severities, counts, or these statuses, CodeRabbit can decide the check from this data without analyzing the code again. If they ask whether a defect exists in the code, the check still looks for evidence in the code. Only threads that CodeRabbit started are included. Comments written by people, and replies in a thread, are not included. On Bitbucket and Azure DevOps, only inline comments on a file are included. If CodeRabbit cannot load the comments, the check is told that they are unavailable.

When a check receives review comments

  • @coderabbitai run pre-merge checks: every custom check receives the posted comments.
  • Automatic runs during a review: CodeRabbit reads each check’s name and instructions to decide whether the check depends on the review’s findings. Checks that depend on them run after the review finishes and receive the comments. The other checks run earlier, without them. No setting controls this; to make sure a check runs after the review, mention CodeRabbit’s review comments or findings in its instructions. If it is unclear whether a check depends on the review, it runs after the review.
  • evaluate custom pre-merge check: test runs do not receive posted comments.
Resolving a thread changes discussion, not code. A check result changes only when the checks run again, after a new commit or @coderabbitai run pre-merge checks. A failed check stays failed until a later run explicitly finds the earlier failure addressed or incorrect, or until you change the check’s instructions.

Define a check in Markdown

On GitHub Cloud with CodeRabbit Cloud, use configuration directories to store a check in .coderabbit/pre-merge-checks/. Put its settings in YAML front matter and its instructions in the Markdown body. You can keep your existing V2 YAML or TypeScript configuration.
.coderabbit/pre-merge-checks/migration-reversal.md
---
id: migration-reversal
name: Migration reversal
paths:
  - "db/migrations/**"
mode: warning
---

Check each new database migration for a matching rollback operation.

Pass if each new migration defines both an up operation and a down operation
that reverses it.
Fail if either operation is missing. Name the affected migration and explain
which operation is missing.
This check applies when a changed file matches db/migrations/**. Because report is omitted, it defaults to platform and publishes its result as a GitHub Check Run. If CodeRabbit confirms that the GitHub App installation lacks Checks write permission, it runs the check and shows the result in the Walkthrough with a permission notice. Add report: coderabbit to always use Walkthrough reporting and CodeRabbit’s native merge controls instead.

Check front matter

The body must contain instructions when enabled is true and cannot exceed 10,000 characters. See front matter for the shared id, name, paths, exclude, and enabled fields, and nested directories for scope and override rules. The check’s display name uses name if present, or id otherwise. These additional fields apply only to checks:
FieldValuesDefaultPurpose
modeoff, warning, errorwarningDisable the check, report a warning, or report a failure.
reportplatform, coderabbitplatformSend the result to a GitHub Check Run or the CodeRabbit Walkthrough.
These are Markdown front matter fields. Do not add report to an inline YAML custom check. See GitHub Check Runs for result states and merge requirements.

Move a check from YAML or the web UI

V3 has no pre_merge_checks YAML section. Author its custom checks in .coderabbit/pre-merge-checks/, keeping .coderabbit/instructions/ for review guidance. Built-in checks are not converted automatically; follow the V3 migration guide to prepare and verify a replacement policy.
  1. Copy the check’s instructions into a Markdown file under .coderabbit/pre-merge-checks/.
  2. Add front matter with a stable id, the existing name, and the same mode. Set report: coderabbit if you want to keep Walkthrough reporting.
  3. Remove the old inline check or set its mode to off in the configuration source that supplies it.
An active inline check and a selected directory check cannot have the same display name. CodeRabbit reports a configuration error instead of choosing one. Inline and directory checks count toward the same plan limit. If their combined active count exceeds that limit, CodeRabbit reports an error; it does not silently drop directory checks.

Limitations

Custom checks run in a sandboxed environment. Instructions that rely on unavailable capabilities will return Inconclusive or produce unreliable results.
Custom checks cannot:
  • Run your test suite — dependencies are not installed in the sandbox
  • Access node_modules, dist, or build artifacts — build steps are not executed
  • Execute arbitrary repository code — security restriction
  • Post inline comments on specific lines — results appear in the Walkthrough or, for directory checks with report: platform, a GitHub Check Run
  • Check PR approval status or reviewer assignments — not available to the agent
  • Modify the CodeRabbit review — use Path Instructions instead

Writing Effective Instructions

Think of instructions as guidance for a smart teammate who needs explicit criteria, not subjective judgment.

Be specific and actionable

Avoid vague instructions like “Check for security issues”

Define clear pass/fail criteria

Say exactly what causes failure

One concern per check

Don’t bundle security, testing, and documentation into one instruction

Include examples for complex rules

Show what passes and what fails
Avoid these anti-patterns:
Anti-patternExampleWhy it fails
Vague instructions”Verify best practices”No concrete pass/fail criteria
Unavailable information”Ensure PR is approved by @security-team”Agent cannot check approval status
Speculation”Assess if there are obvious performance optimizations”No definitive criteria; relies on subjective judgment
Review modifications”Keep review comments concise”Use Path Instructions instead

Examples

Custom checks can enforce a wide range of guardrails tailored to your team’s needs. Here are a few examples to get you started.

Severity Gate

Fail if any CodeRabbit review comment or new finding with Critical or Major
severity does not have a confirmed code fix (code=addressed).
A new finding from the current review has no code status and counts as not fixed.
A resolved discussion alone does not count as fixed.
If the code may have changed since a comment was assessed, inspect the current code.
Ignore Minor, Trivial, and Info comments.
Set this check to error mode with Automatic Approvals to withhold CodeRabbit approval for Critical and Major findings without a confirmed code fix. Other approval requirements and your Git provider’s merge requirements still apply. See Gate on CodeRabbit review comments.

Sensitive Data in Logs

Fail if any log statement may include passwords, API keys, tokens,
SSNs, or payment card data. Check print(), console.log, logger.*,
System.out.println, and fmt.Print variants.

Hardcoded Credentials

Scan for hardcoded credentials matching: sk_live_*, AKIA[A-Z0-9]{16},
ghp_[a-zA-Z0-9]{36}, or variables named *_SECRET, *_KEY, *_PASSWORD.
Exclude test files and .example files.

Database Migrations

For files in db/migrations/: verify both up() and down() methods exist.
Flag migrations dropping tables without restoration in down().

Breaking Changes

All breaking changes to public APIs, CLI flags, environment variables,
or database schemas must be documented in the "Breaking Change" section
of the PR description and in CHANGELOG.md.

Language Migration Policy

Disallow creation of new Java source files. Java may be modified,
but new code should be written in Kotlin.

Pass: PR modifies existing .java files or adds no new .java files.
Fail: A new *.java file is added to source control.
