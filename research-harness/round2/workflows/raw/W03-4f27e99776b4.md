# Automations

> Set up Devin automations: event-driven workflows that start Devin sessions from Slack, Microsoft Teams, GitHub, Linear, schedules, and webhooks.

Automations let you wire external events — Slack messages, Microsoft Teams messages, GitHub webhooks, Linear ticket updates, schedules, and custom webhooks — to Devin sessions that start automatically. Instead of manually tagging Devin every time a bug is reported or a CI check fails, you define the trigger once and Devin handles each event as it arrives. You can also manage automations declaratively with the [Terraform provider](https://docs.devin.ai/api-reference/terraform-provider.md). For a video walkthrough with four examples, see the [Devin Automations tutorial](https://docs.devin.ai/tutorial-library/automations.md).

## Core concepts

An automation has a trigger and actions, with optional conditions and a Preflight check:

| Part | What it does |
| - | - |
| **Trigger** | The event that fires the automation (e.g. a Slack message in `#bugs`, a GitHub CI failure, a Linear label change) |
| **Conditions** | Optional filters that narrow the trigger (e.g. only fire when the label is `bug`, only for a specific repo) |
| **Preflight check** | An optional LLM filter or script that runs after an event matches, before the actions. It can skip the event or let it through; a script can also produce separate work items. |
| **Action** | What Devin does when the trigger fires — start a new session, message an existing session, or act as a triage monitor |

### Action types

| Action | Description |
| - | - |
| **Start session** | Creates a new Devin session with the prompt you define. The event payload is automatically included as context. |
| **Message session** | Sends a message to an existing, long-running Devin session — useful for feeding events into a session that maintains state. |
| **Triage Devin** | A persistent Devin that monitors a Slack channel. It watches every incoming message, decides what needs attention, and spawns child sub-devins for items that require investigation. See [Auto-triage](https://docs.devin.ai/product-guides/auto-triage.md) for details. For alerts, incidents, and bug reports, use [Devin Oncall](https://docs.devin.ai/product-guides/devin-oncall.md). |
| **Email notification** | Sends you an email when the automation runs — on every run, only on failures, or only on successes. |

### Trigger sources

| Source | Event types | Example use case |
| - | - | - |
| **Slack** | New message, reaction added | Triage bug reports in `#incidents`, react with 🚨 to start an investigation |
| **Microsoft Teams** | Message posted, reaction added | Watch a Teams channel for bug reports or requests and have Devin answer in the thread. See [Microsoft Teams triggers](#microsoft-teams-triggers) |
| **GitHub** | Issue, issue comment, PR opened/updated, PR review, check run (CI), push | Auto-fix CI failures, respond to `/devin` comments on issues |
| **GitLab** | Merge request, MR comment, issue, issue comment, push, pipeline | Auto-fix failing pipelines, respond to comments on merge requests |
| **Linear** | Issue created, label added, status changed, priority changed, assigned, moved to a team | Triage bugs when labeled, implement tickets when assigned to Devin |
| **Jira** | Issue created, issue updated, label added, status changed, assigned, commented | Implement tickets when assigned to Devin, track status changes |
| **Pylon** | Issue created, tag added, status changed | Triage customer bug tickets filed in Pylon. See the [Pylon integration](https://docs.devin.ai/integrations/pylon.md) |
| **PagerDuty** | Incident triggered, acknowledged, resolved, updated | Investigate high-urgency incidents as soon as they fire. See the [PagerDuty integration](https://docs.devin.ai/integrations/pagerduty.md) |
| **Schedule** | Recurring (cron-based) or one-time (run once) | Daily Sentry error sweeps, weekly dependency updates, nightly smoke tests, or a one-off task that runs at a specific future time |
| **Webhook** | Incoming HTTP request | Wire any external system (PagerDuty, Datadog, Sentry, custom tools) to Devin via a webhook URL |

Non-schedule sources appear in the trigger picker once the corresponding integration is connected in **Settings > Connections**.

An admin can limit which of these sources may start automations with a [trigger policy](#trigger-policies).

A single automation can have **multiple triggers** — they act as an OR, so the automation fires when any of its triggers match. For example, you can have one automation that fires on both a GitHub CI failure and a Slack reaction.

## Creating an automation

### From the automations page

1. Navigate to **Automations** in the sidebar
2. Click **Create automation** and choose **Create** to open a blank editor (if you have no automations yet, click **Create manually** on the landing page instead). The same menu also offers **Template** (opens the template gallery) and **Generate with Devin** (starts a session that builds the automation with you)
3. Configure the trigger, conditions, and action
4. Click **Create automation**

### From a template

1. Navigate to **Automations** in the sidebar
2. Click **Create automation** > **Template** (if you have no automations yet, click **Create from template** on the landing page instead), or go directly to `/automations/templates`
3. Browse the template gallery — each template is a pre-configured automation for a common workflow
4. Click a template to pre-fill the editor with its trigger, action, and suggested limits
5. Customize the configuration (e.g. select your Slack channel or repo) and click **Create automation**

### Using natural language

On the automations page, click **Create automation** > **Generate with Devin** (if you have no automations yet, click the **Generate with Devin** card on the landing page instead). Devin opens a new session to help you build the automation. Describe what you want — for example, "When a CI check fails on my-org/my-repo, have Devin fix it and push to the same branch." Devin will generate the automation configuration for you, which you can review and create.

If you work with a [Devin Bot](https://docs.devin.ai/work-with-devin/bots), you can also ask the Bot in chat to run something on a schedule or when something happens. The Bot sets up the automation and lists it on the **Automations** page of its settings.

## Configuring triggers

### Slack triggers

Slack triggers fire when a message is posted or a reaction is added in a channel where Devin has been invited. To give your team a dedicated handle to @-mention instead, see [Use a Devin Bot in Slack](https://docs.devin.ai/work-with-devin/bots/slack.md).

* **Slack message**: Fires on new messages. A channel condition is added by default; you can remove it to match messages across channels, but every condition group then needs at least one other filter (for example message text or sender type — **Include thread replies** alone is not enough).
* **User group mentioned**: Fires when a Slack user group (for example `@oncall`) is mentioned. Select the group or enter its Slack ID (starts with `S`), and optionally limit it to specific channels.
* **Slack reaction**: Fires when a specific emoji reaction is added to a message (e.g. 🚨 for incidents). You can filter by the reaction name and the channel.

> [!NOTE]
>
> For channel-scoped triggers, Devin must be invited to the Slack channel. You must also have your personal Slack account connected in **Settings > Connections > Slack**.

### Microsoft Teams triggers

Microsoft Teams triggers fire when a message is posted or a reaction is added in a Teams channel. They appear in the trigger picker once the [Microsoft Teams integration](https://docs.devin.ai/integrations/microsoft-teams.md) is connected.

* **Message** (`teams:message`): Fires on new messages in the selected channel. By default it matches only top-level posts; turn on **Include thread replies** to also match replies in a thread. You can narrow it further by **User**, **Message text** (for example contains, or a regular expression), and **Sender type** (human or bot).
* **Reaction added** (`teams:reaction_added`): Fires when a specific reaction is added to a message in the selected channel (for example 👀). You must choose the reaction. By default it matches only reactions on top-level posts; turn on **Include thread replies** to also match reactions on replies. You can also filter by the **User** who reacted.

Every condition group on a Teams trigger must select a **Team** and a **Channel**. A Teams trigger cannot watch every channel at once: select each channel you want it to watch.

When the automation starts a session, the trigger's reply (`post_response` in the API) posts Devin's final response in the same Teams thread as the message or reaction that triggered it. People can then @mention Devin in that thread to continue the same session.

> [!NOTE]
>
> Teams triggers work only in teams where the Devin app is installed with [resource-specific consent (RSC)](https://docs.devin.ai/integrations/microsoft-teams.md#rsc-not-granted) granted. Shared channels, direct messages, and group chats cannot trigger automations. Edited or deleted messages, removed reactions, and Devin's own messages do not fire triggers.

Standard channels support both trigger types. A private channel supports only a **Message** trigger that runs when Devin is @mentioned, because Teams delivers a private channel's messages to Devin only when they mention it:

* When you pick a private channel (shown with a lock icon), the editor adds the **Devin is mentioned** condition and locks it. Messages that do not mention Devin, and reactions, never fire the trigger.
* You must be a member of the private channel itself, not only of its team.
* Devin checks that membership when you save. If saving fails because Devin can't check who is in the channel, update the Devin app in the team, add it to the private channel, and save again.

In a private channel, an automation with a **Start session** action answers the mention itself, and Devin does not start a separate session.

### GitHub triggers

GitHub triggers fire on repository events. You must select a specific repository for each trigger.

* **Issue**: Fires on issue events (opened, closed, reopened, edited, labeled).
* **Issue comment**: Fires when a comment is posted on a GitHub issue. Commonly used with a `starts_with "/devin"` condition so users can type `/devin` on any issue to trigger Devin.
* **Pull request**: Fires on PR events (opened, synchronized, etc.).
* **Pull request review**: Fires when a review is submitted on a PR.
* **Pull request review comment**: Fires on individual review comments.
* **Check run (CI)**: Fires when a CI check completes. Filter by `conclusion = failure` to auto-fix broken builds.
* **Push**: Fires on pushes to a branch.

> [!NOTE]
>
> By default, a GitHub connection's **Automation scope** is **Private repos only**, so GitHub automations only fire on private repositories. An admin can opt an individual GitHub connection into public repositories: in [Settings → Connections → GitHub](https://app.devin.ai/settings/connections/github), click the connection and, on its **General** tab, change it to **All connected repos**. Anyone on the internet can comment on or open a PR against a public repo, so public-repo triggers carry a higher prompt-injection risk — enable this deliberately and keep your trigger conditions narrow.

### GitLab triggers

GitLab triggers fire on project events in your connected GitLab instance:

* **Merge request**: Fires on MR actions (opened, closed, merged, reopened, approved, updated).
* **MR comment**: Fires when a comment (note) is posted on a merge request, including diff review threads.
* **Issue**: Fires on issue actions (opened, closed, reopened, updated).
* **Issue comment**: Fires when a comment is posted on an issue.
* **Push**: Fires on pushes to a branch.
* **Pipeline**: Fires when a pipeline reaches a given status — filter by status (e.g. `failed`) to auto-fix failing pipelines.

### Linear triggers

Linear triggers fire on issue events in your connected Linear workspace. You must select a team for each trigger.

* **Issue created**: Fires when a new issue is created in the selected team.
* **Label added**: Fires when a label is applied to an issue (e.g. `bug`, `devin`).
* **Status changed**: Fires when an issue's status changes (e.g. moved to "In Progress").
* **Priority changed**: Fires when an issue's priority changes.
* **Assigned**: Fires when an issue is assigned to someone.
* **Issue moved**: Fires when an issue is moved to a different team — the trigger's team filter matches the destination team.

### Jira triggers

Jira triggers fire on issue events in your connected Jira site. You can filter by project, labels, status, assignee, and epic:

* **Issue created**: Fires when a new issue is created.
* **Issue updated**: Fires when an issue's fields change.
* **Label added**: Fires when a label is applied to an issue.
* **Status changed**: Fires when an issue's status changes.
* **Assigned**: Fires when an issue is assigned to someone.
* **Comment created or edited**: Fires when a comment is added or edited on an issue.

### Schedule triggers

Schedule triggers fire on a time-based schedule — either recurring or as a single one-time run. In the trigger dropdown, expand **Schedule** and choose **Every hour**, **Every day**, **Every week**, **Run once**, or **Custom schedule**.

* **Recurring**: Set the frequency (hourly, daily, weekly) and time. Under the hood, schedules use the iCalendar RRULE format. Choose **Custom schedule** to build a custom recurrence (repeat every N minutes/hours/days/weeks/months) or enter a raw RRULE string directly (e.g. `FREQ=WEEKLY;BYDAY=MO;BYHOUR=9;BYMINUTE=0`) for more complex cadences.
* **Run once**: Fires a single time at a specific future date and time, then automatically disables itself. Useful for one-off delayed work — e.g. "wake Devin up in 12 hours to run a task." Pick the date and time (defaults to one hour from now); it must be in the future.

> [!TIP]
>
> Each schedule has its own time zone, which defaults to your browser's time zone and can be changed in the schedule editor. The schedule runs at that local time, including across daylight saving changes.

### Webhook triggers

Webhook triggers let you connect any external system to Devin via a unique HTTPS endpoint.

1. Create an automation with a **Webhook** trigger
2. Copy the webhook URL and secret shown in the trigger configuration
3. Configure your external system (PagerDuty, Datadog, Sentry, or any custom tool) to send HTTP POST requests to this URL
4. Optionally add a **payload filter** — a regex pattern that the request body must match for the automation to fire

Pass the webhook secret in any one of these ways:

* `X-Webhook-Secret: <secret>` header
* `Authorization: Bearer <secret>` header
* `?secret=<secret>` query parameter

Prefer a header — query strings are often captured in proxy, CDN, and server access logs.

The webhook payload is included in the Devin session prompt as context. Payloads larger than 200 KB are automatically truncated.

#### Webhook secret

Every webhook trigger has a secret that authenticates incoming requests — calls without the correct secret are rejected. The secret is generated for you and shown when you add the webhook trigger in the automation editor.

> [!NOTE]
>
> Copy the secret when it's shown — it will not be shown again. A lost secret cannot be recovered; regenerate it instead.

Each request must include the secret in the `X-Webhook-Secret` HTTP header. For example, to test with curl:

```bash theme={null}
curl -X POST '<webhook-url>' \
  -H 'Content-Type: application/json' \
  -H 'X-Webhook-Secret: <secret>' \
  -d '{"test": true}'
```

If you lose the secret or need to rotate it, open the webhook trigger in the automation editor and regenerate it. The old secret stops working immediately, so update your external system with the new value.

## Preflight checks

A **Preflight check** is an optional step that runs between a matched trigger and the automation's actions. An automation can have one of two kinds:

| Kind | What it does |
| - | - |
| **LLM filter** | A decision model reads each matched event and skips the ones that don't match your plain-language description. Fast and cost-effective. |
| **Script** | Your own Python, Node, or Bash code decides what happens: call an external service, keep state between runs, or start a session for each new item. |

To add one, click **Add a preflight check before the agent runs** below the trigger section and choose **LLM filter** or **Run a script**.

Choose by what the check has to know:

* **Is this event the kind I want?** Use an **LLM filter**. It judges one event at a time and remembers nothing between events, so it cannot tell a new item from one it has already seen.
* **Is there anything new since last time?** Use a **script**. It keeps state between runs, so it can hold a cursor or the IDs it has handled: it reads a JSON object from `STATE_FILE`, and what it writes back is there on the next run. See [Keep state between runs](#keep-state-between-runs). On a schedule trigger this is the only kind that can skip a run with nothing new.

A script has no MCP servers and no Devin tools. It reaches other services only through network requests it makes itself, such as an HTTP API call, using the secrets you attach and within the automation's network restrictions. If the check needs a connection that only an MCP server provides, let the automation run and have the session it starts do that check.

> [!NOTE]
>
> Preflight scripts are being rolled out. If **Run a script** is not offered, scripts are not enabled for your organization yet.

> [!WARNING]
>
> The automation's **Run now** button bypasses the Preflight check and runs the configured actions directly.

### LLM filter

Select **LLM filter** and describe what events to filter in or not. For example: "PRs about the auth service", or "Slack messages about dinner".

The lightweight decision model reads the whole event. Only events that match will run the agent. It sees only that event: no earlier events, no saved state, and no tools.

### Configure and test a Preflight script

The script runs in a separate, short-lived virtual machine (VM), not inside the Devin session it may start. It can read the event, keep a small amount of state between runs, and decide what work reaches the configured actions.

1. Create an automation or edit an existing one, and configure its triggers and conditions.
2. Click **Add a preflight check before the agent runs** and select **Run a script** in the **Preflight check** card.
3. Click **Edit script**, choose **Python**, **Node** (JavaScript), or **Bash** in the runtime selector, and edit the starter script.
4. If needed, use **Select secrets** in the script editor to attach organization secrets. Only the selected secrets are injected as environment variables. Saving or testing a script with attached secrets requires permission to manage organization secrets.
5. Set **Timeout (seconds)** in the card: the default is 60 seconds, and the allowed range is 1–300 seconds. The script uses the **Minimal environment** by default; if machine snapshots are available, the **Environment** selector also lets you choose an organization snapshot with your dependencies.
6. In the script editor, choose an event under **Test against** and click **Run**. You can test the unsaved script against a sample of a configured trigger, or against a recent event for an existing automation. Review the result, logs, and, for emitted items, the preview of how many would run, be duplicates, or be deferred.
7. Click **Save script** to apply the editor changes, then **Create automation** or save the automation to persist the configuration.

Test runs execute your script, but do not run the automation's actions, persist changes to its saved state, or mark emitted items as handled. Any external requests or side effects performed by your script are real. For example, testing a script that writes to an external service will still perform that write.

### Script input and output

The script receives these environment variables. Each contains a file path, not the JSON data itself:

| Variable | Contents |
| - | - |
| `EVENT_FILE` | Read-only JSON event with `event_type`, `source`, `payload`, and `received_at`. The `payload` shape depends on the trigger. |
| `STATE_FILE` | A read/write JSON object persisted between successful live runs, up to 64 KiB. Use it for a polling cursor, not a database. |
| `LAST_RUN_FILE` | Read-only feedback about previously emitted items: their `key`, `status`, and `session_id` when present. It contains up to the 200 most recent items and a `truncated` indicator. |
| `OUTPUT_FILE` | The JSON decision your script must write before exiting successfully. |

Write exactly one of `run` or `items` to `OUTPUT_FILE`, optionally with a string `reason`:

| Output | Behavior |
| - | - |
| `{"run": true}` | Run the configured actions once, with the original event. |
| `{"run": false, "reason": "Alert already resolved"}` | Skip the event without running its actions. |
| `{"items": [{"id": "INC-1", "title": "Investigate error spike"}]}` | Run the configured actions separately for each accepted item. With **Start session**, this starts one session per item; each session receives the original event plus that item as additional context. |
| `{"items": []}` | Skip the event because there is no work. |

For example, this Python script lets a Slack message through only if its text contains `urgent`:

```python theme={null}
import json
import os

with open(os.environ["EVENT_FILE"]) as f:
    event = json.load(f)

text = event.get("payload", {}).get("text", "")
should_run = "urgent" in text.lower()

with open(os.environ["OUTPUT_FILE"], "w") as f:
    json.dump({"run": should_run, "reason": "Urgency filter"}, f)
```

Select a Slack message sample or recent Slack message in **Test against** to inspect the result. Printing a decision to standard output is not enough: the script must write valid JSON to `OUTPUT_FILE` and exit with code 0.

### Keep state between runs

`STATE_FILE` holds a JSON object, which is `{}` on the first run. Read it when the script starts, and before exiting write back the object the next run should see. After a failed run or a test run, the next run reads the old state. Do not store secrets in it.

For example, this Python script on a schedule trigger polls an alert service that returns alerts oldest first, and starts a session only for alerts that arrived since the last run:

```python theme={null}
import json
import os
import urllib.parse
import urllib.request

with open(os.environ["STATE_FILE"]) as f:
    state = json.load(f)

cursor = urllib.parse.quote(str(state.get("cursor", "")))
request = urllib.request.Request(
    "https://alerts.example.com/api/alerts?after=" + cursor,
    headers={"Authorization": "Bearer " + os.environ["ALERTS_API_TOKEN"]},
)
with urllib.request.urlopen(request) as response:
    # Take no more than the per-run item cap, so the cursor never passes an alert deferred over the cap.
    alerts = json.load(response)["alerts"][:10]

with open(os.environ["OUTPUT_FILE"], "w") as f:
    json.dump({"items": [{"id": a["id"], "title": a["title"]} for a in alerts]}, f)

if alerts:
    state["cursor"] = alerts[-1]["id"]
    with open(os.environ["STATE_FILE"], "w") as f:
        json.dump(state, f)
```

With no new alerts the script writes `{"items": []}`, so the run is skipped and no session starts. The cursor moves when an alert is emitted, not when its session succeeds, so this script does not emit again an alert whose run fails or is skipped; read `LAST_RUN_FILE` to retry those. `ALERTS_API_TOKEN` is a secret attached to the script, and `alerts.example.com` must be allowed by the automation's network restrictions.

### Script items, state, and limits

* **Duplicate prevention:** An item's `id` identifies a unit of work within this automation, not just an entity. `{"id": "INC-1"}` is handled once; add a `version`, such as the upstream update timestamp, to process a new occurrence of that incident. Without an `id`, Preflight identifies the item by a hash of its contents, so changing the contents can cause another run.
* **Per-run item cap:** By default, at most 10 new items are dispatched per run; the system's maximum cap is 50. Items beyond the cap are not handled and are not automatically scheduled. Your next script run must emit them again. Do not advance a cursor past deferred work just because it appeared in your output.
* **Previous outcomes:** Use `LAST_RUN_FILE` to distinguish running, succeeded, failed, or skipped work. An item whose run fails is released, so a later script run can emit it again.
* **Persistent state:** Live script runs for an automation execute one at a time. Failed scripts do not advance saved state or mark items as handled. **Clear state** clears both the saved JSON state and already-handled item history; previously handled items can run again after this reset.
* **Size limits:** Script source and output are each limited to 256 KiB, saved state to 64 KiB, and captured logs to 1 MiB.
* **Failures:** A nonzero exit, timeout, invalid output or state, or infrastructure failure stops that event before its actions. There is no automatic retry of the script for that event; a later trigger can run it again.
* **Network access:** The script's VM follows the automation's network restrictions and applicable [security profile](https://docs.devin.ai/product-guides/security-profiles.md). For example, polling an external alert service requires its host to be allowed. Attaching a secret does not grant network access.

## Configuring actions

### Start session

The most common action. When the trigger fires, Devin starts a new session with your prompt. The event payload (e.g. the Slack message text, GitHub webhook body, or Linear ticket details) is automatically appended to the prompt so Devin has full context.

Options:

* **Prompt**: The instructions Devin follows. Write this like you would a normal Devin prompt.
* **Skill** (optional): Use `@skills:<name>` in your prompt to run a [skill](https://docs.devin.ai/product-guides/skills.md) for additional instructions.
* **Tags** (optional): Add tags to sessions created by this automation for easy filtering.

### Message session

Sends a message to an existing, long-running Devin session. Useful when you want a single persistent session to process events over time instead of spawning a new session for each event.

You must select the target session when configuring this action.

### Triage Devin (monitor)

Creates a persistent Devin session that monitors a Slack channel. See the [Auto-triage guide](https://docs.devin.ai/product-guides/auto-triage.md) for full details on this action type.

### Email notification

Sends an email notification when the automation runs. Choose when to notify:

* **Always** — on every invocation
* **On failure** — only when the session fails or errors
* **On success** — only when the session completes successfully

## Limits and safeguards

Automations include built-in controls to prevent runaway usage:

### Spend limit per session

Set the most a single session started by this automation can use. The field is **Spend limit per session**, in dollars, on usage-based plans, and **ACU limit per session** on plans billed in ACUs, such as Enterprise. If Devin hits the limit, the session stops. This prevents any single run from consuming excessive resources.

### Rate limit

Set a cap on how many times the automation can run within a rolling time window. For example, "at most 10 runs per hour" prevents a noisy Slack channel or a flurry of CI failures from spawning dozens of sessions.

Both fields are optional — if cleared, the automation runs without that limit. New automations start with no per-session limit and a **Rate limit** of 50 runs per hour (150 per hour for Slack channel-watching triage automations); templates apply the same defaults.

### Queueing

By default, every matching event starts a run right away. Turn on **Enable queueing** in the automation editor to limit how many runs happen at once:

* **Concurrent runs**: The maximum number of runs of this automation at one time. Extra events wait in the queue. A run stops counting toward the limit as soon as its session finishes and is waiting for new instructions.
* **Queue depth**: The maximum number of events that can wait in the queue. Events that arrive when the queue is full are dropped.

Queued runs appear with a **Queued** status in the automation's activity.

### Network policy

You can enable a network policy to restrict which external hosts the automation's sessions can access. This is especially important for automations that process untrusted user input (e.g. Slack messages, webhook payloads). You can add specific domains to the allowlist if Devin needs to reach external services. An automation's network policy only ever narrows access: it is intersected with the [security profile](https://docs.devin.ai/product-guides/security-profiles.md) governing the automation's sessions.

### Trigger policies

An admin can choose which trigger sources may start automations, for example to stop automations that start from Slack messages. This needs the **Manage trigger policies** permission, which account admins have.

1. Go to [Settings > Automations](https://app.devin.ai/settings/automations?tab=trigger-policies) and open the **Trigger policies** tab
2. Click **Restrict sources**
3. Select the sources to allow and click **Save**

To lift the restriction, delete the policy from its menu.

With a policy in place:

* A source added later is blocked until you allow it.
* A blocked source is locked in the trigger picker, with the tooltip **Blocked by a trigger policy**.
* Enabled automations stay enabled, but their triggers on a blocked source no longer start them. Before saving, you see the automations the change would block.

A policy covers the sources that bring in events from outside Devin. Schedule triggers, and any other trigger on something that happens inside Devin, are always allowed and can't be blocked. It applies only to automations: mentions of Devin in Slack, Microsoft Teams or GitHub, the API, the CLI and playbooks are not affected.

On an Enterprise plan, the tab is in the enterprise settings. **Set up default policy** creates the policy every organization follows, and **Add policy** gives the organizations you assign to it a different set of sources.

## MCP integrations

> [!TIP]
>
> Connecting MCP integrations is highly recommended — they dramatically improve automation quality by giving Devin access to runtime data like logs, metrics, and error details.

Automations work with [MCP integrations](https://docs.devin.ai/work-with-devin/mcp.md) to give Devin access to external tools. When creating an automation, the **Connections** section shows which MCP servers are recommended and their connection status.

For example, the "Fix Sentry Errors Daily" template recommends the Sentry MCP so Devin can query Sentry for unresolved errors. The "Investigate Alerts Triggered" template recommends the Datadog MCP for pulling metrics and traces.

Enable MCP servers on the **Settings → Connections → MCPs** tab (or install their plugins from the plugin marketplace) before creating automations that need them.

## Slack tool access

By default, automation sessions can read and write to the Slack channels involved in the trigger. You can grant access to additional Slack channels in the **Slack tools** section of the automation editor. This is useful when Devin needs to read from multiple channels beyond the one that triggered the automation.

## Activity and monitoring

Each automation tracks its invocation history. On the automation detail page, the **Events** tab shows:

* Recent invocations with timestamps
* Whether each invocation succeeded or was skipped
* Links to the Devin sessions that were created
* Error messages for failed invocations

To check what an automation costs, open its **Consumption** tab. It charts the usage of the automation's sessions for each day in the selected date range. On plans with an included quota, the chart shows on-demand usage only: usage covered by your plan is not shown.

The automations list page shows a sparkline for each automation, giving you a visual overview of activity over the past 30 days.

## Enabling and disabling

Toggle an automation on or off at any time from the automations list or detail page. Disabled automations stop processing events but retain their configuration. Re-enabling an automation resumes event processing immediately.
