Configuration and administration

Customizing the agent

The agent discovers a lot on its own through Deep Search: which package manager a repository uses, how CI is wired, and where similar migrations have been done before. But internal policies may not be written in the code: which base images you allow, how you name branches, which approvals a dependency bump needs, or what a good commit message looks like in your organization.

You can add guidance on the Agents page of your Batch Changes settings, at sourcegraph.example.com/users/<username>/settings/batch-changes/agents. Administrators add instance-wide guidance at sourcegraph.example.com/admin/batch-changes/agents, and organizations can carry shared guidance in their settings. Entries from all three levels combine.

Deep Search uses its own guidance and skills, even when called by Agentic Batch Changes. Configure them separately in Deep Search settings.

To give the agent access to systems outside your code, such as issue trackers, internal documentation, or CI, add connectors.

Guidance and skills

Guidance and skills configured here apply only to the coordinating agent you talk to directly, which researches your codebase, writes the plan, and manages the rollout.

Guidance is AGENTS.md-style text the agent sees on every run, before it reads your first message. Use it for rules that should always apply: house style, forbidden actions, default tools, and how to phrase changeset descriptions. Keep it short. Everything in guidance competes for the agent's attention on every turn, and the combined guidance is truncated at 32 KiB.

A skill is a named document the agent loads on demand when a task matches its description. Skills suit procedures that only matter some of the time: how to run your internal CI, how to upgrade a particular framework, or how your monorepo is laid out. A skill's content only uses context when it is loaded.

Repository-backed skills can include supporting files, such as references, assets, or scripts. The coordinating agent can read these files when their source is accessible, but it does not execute bundled scripts directly. To run code, it must put that work in an execution step.

Loading guidance from a repository

To load repository-backed guidance or skills, configure a repository source in your Agents settings. The coordinating agent reads these configured sources; it does not automatically load guidance from every repository in the batch change.

The source repository must be available through Sourcegraph, but it does not need to be search-indexed. The agent reads the configured source path on the selected branch. If no branch is specified, it uses the repository's default branch.

Keeping guidance in a repository lets changes go through code review and lets teams share guidance without sharing settings. The agent reloads configured sources when it processes a message, so changes on the configured branch take effect on the next turn. It does not reload them between individual tool calls within that turn.

Precedence

Guidance loads in settings order: site, then organization, then user, so your own guidance appears after your administrator's. If you belong to multiple organizations, their settings load in organization ID order.

Skills with distinct names are combined. Skill names are case-insensitive. When two skills share a name, the last one loaded wins: your skill overrides an organization's, which overrides the site's, and any of them can override a Sourcegraph default.

What to put in guidance

Write guidance the way you'd brief a new colleague who is very capable and knows nothing about your organization. The most useful entries are the ones the agent can't infer from code:

  • Image policy. Which base images to prefer, whether the agent may build images or should stick to stock ones.
  • Publication conventions. Branch name patterns, changeset title format, required labels or reviewers, and whether to open drafts or ready-for-review changesets by default.
  • Verification. Which commands count as "tests pass" for each ecosystem, and which are too slow to run before publishing.
  • CI. How to fetch logs for a failed build and what to try first. This is what the agent uses when it sets up CI handling for you.
  • Boundaries. Repositories or directories the agent should never modify, and changes that always need a human to sign off.

Avoid restating the agent's own defaults. It already researches before planning, tests on one repository before expanding, and asks before publishing, so guidance that repeats those rules adds length without changing behavior.

Changeset hooks

Agentic Batch Changes introduces changeset hooks, which allow programmable responses to events like CI failures and merge conflicts. For example:

  • When CI fails, the agent can prepare a script to fetch CI logs for you. This data can be used to amend the agent's plan, or be handed off to a coding agent to fix immediately.
  • When a merge conflict is encountered, the agent can ask a coding agent to address it.

To get set up, ask the agent for it in your agentic batch change. Fetching CI logs requires a hook step that uses your CI credential; attempting fixes automatically also requires a coding agent step in that hook. Detecting a failed check does not configure either action automatically. Encode processes that work for your organization in guidance or skills.

Coding agent steps

The coding agent step is a native step type for Agentic Batch Changes that lets the agent delegate non-deterministic or context-dependent changes to another coding agent. Coding agent steps are automatically pre-configured with the Sourcegraph MCP.

Within a coding agent step, the agent has:

  • Full MCP access under your identity. The Sourcegraph MCP tools are available and authenticated as you, so the agent operates with your permissions.
  • Access to the code being worked on. The workspace's repository checkout is available to the agent as it makes changes.
  • Your connectors. If you have user or shared connectors configured, the agent can call their tools with your connections.

We currently support Claude Code and Codex as native coding agent steps.

Codex is the default. You can request either agent in your prompt or guidance; the coordinating agent selects it in the plan.

Coding agent LLM traffic is routed through the Sourcegraph Model Provider.

Agentic Batch Changes does not use coding agent steps for every task. For deterministic changes, the agent will opt to write a script, or even an entire program, to efficiently apply some or all of the target changes.

Security and secrets

The agent acts as you. Everything it reads, it reads with your repository permissions, so it can't scope a change to a repository you can't see. Everything it publishes, it publishes with your Batch Changes credential, or the global credential your administrator configured. Your code host's branch protection, required checks, and review rules apply unchanged.

Approvals

The agent researches, plans, and revises freely without publishing changes to your code host. Running the plan for the first time usually takes an explicit yes or instructions from you. Publishing, expanding the rollout, and fanning out to everything that remains may each need a reply, unless you authorized them up front in your prompt.

When a new or changed step uses a secret, the agent shows you that step and waits for your approval before running it with your credential. You choose how far the approval extends: this run only, this agent, or all of your agents.

Secrets

Some steps need credentials: a package registry token for private dependencies or an API key for reading CI logs. These are managed on two settings pages:

  • Your own secrets live under Secrets in your Batch Changes settings, at /users/<username>/settings/batch-changes/secrets.
  • Administrators manage global secrets, available to every user, at /admin/batch-changes/secrets.

Your own secret takes precedence over a global one with the same name.

Organization-level secrets aren't available to Agentic Batch Changes. Use a user or global secret instead.

A step references a secret by name. Sourcegraph injects the value when the step runs and redacts it from logs; the value never appears in the plan, in the conversation, or in anything the agent reads. The agent never asks you to paste a secret into the conversation: when a step needs a credential that doesn't exist yet, it points you to the settings page and the least-privilege scope the token needs, then waits until you confirm it's there.

Isolation

All code-modifying work runs in isolated containers on Sourcegraph executors, one per repository. A container sees the repository and the secrets its steps reference. It has no direct access to code host credentials, other users' secrets, or other repository checkouts. Coding agent steps can still use Sourcegraph MCP to access code with your permissions. Containers can't publish. Publication happens inside Sourcegraph.

Context filters

Administrators can exclude repositories from the agent's Sourcegraph tools with context filters, configured under experimentalFeatures.agents.contextFilters. Excluded repositories are hidden from the agent's research and from the Sourcegraph MCP tools in its coding agent steps, and are dropped from the agent's workspaces.

Audit log

Agent activity is recorded in the Sourcegraph audit log under the batchChangeAgents entity, with identifiers and no URLs, links, or tokens. On self-hosted instances, route it as you route the rest of the audit log.

Administration

Access

Users need two permission pairs from the Batch Changes namespace in role-based access control:

  • Batch Changes: Read together with Batch Changes: Agent Read to view agents and their conversations.
  • Batch Changes: Write together with Batch Changes: Agent Write to create and run them.

Both halves of a pair are required. All four are part of the built-in User role, so every user has access once the feature is enabled. To roll it out gradually, remove the agent permissions from the User role and grant them through a role of your own.

Ownership

Each agentic batch change has one owner: the user who created it, until it is handed over. Only the owner can send messages, approve actions, run workspaces, and publish. Other users can read the conversation, the plan, and the results, but they cannot change anything; see Sharing and visibility. There is no co-ownership. Because the agent acts as its owner, the owner's repository permissions and Batch Changes credentials bound what it can touch.

Handing over an agent

A handover makes another user the owner of an agent and its batch change. Use it when the owner leaves the team, is on leave, or when the work moves to someone else.

Who can hand over an agent:

  • The owner, from Share > Hand over on the agent page.
  • An administrator, for any agent, including agents of deleted users. They use Share > Hand over on the agent page, or ... > Hand over… in the row on the Threads page.

To hand over, find the new owner by username or display name, then confirm. Any user on the instance can become the new owner. Before you confirm, Sourcegraph checks the new owner's repository permissions and warns you when the new owner cannot read some of the agent's workspaces.

A handover changes the following:

  • The new owner can message the agent, run workspaces, and publish changesets. The agent acts with the new owner's repository permissions and Batch Changes credentials from then on. Changesets the agent publishes or updates after the handover use the new owner's credentials.
  • The batch change moves to the new owner's namespace. Its URL changes to /users/<new-owner>/batch-changes/<name>.
  • The previous owner keeps read access to the agent, also with the link-only site setting, but cannot act on it. The agent page shows who created the agent and who owns it now.
  • The share link stays the same.
  • Workspaces in repositories the new owner cannot read are hidden from the new owner and from the agent. The agent gets a note about the handover and the hidden workspaces. The agent cannot update changesets in those repositories. Changesets that were already published there stay open on the code host.
  • The new owner gets a notification in Sourcegraph. If the agent is waiting for an answer, the open question moves to the new owner.
  • The audit log records the handover with the action ownershipTransferred, the previous owner, the new owner, and the user who did the handover. forced is true when an administrator handed over an agent they do not own.

A handover is refused when:

  • The agent is still working: a message is processing, workspaces are running, or changesets are being published or updated. Wait until the agent is idle or waiting for input, then try again.
  • The new owner already has a batch change with the same name. One of the two batch changes needs another name first.

A handover moves one agent at a time. To get an agent back, ask the new owner or an administrator to hand it over to you.

Threads page

Administrators see every agent on the instance under Administration > Batch Changes > Threads, independent of the sharing setting. The page lists each agent with its owner and status. Filter by owner, status, or title, open an agent, or hand it over from the ... menu in its row.

Sharing and visibility

By default, each user sees only their own agents. To let other users read an agent, the owner opens Share on the agent page and copies the link. Any user with access to Agentic Batch Changes can open the link.

Administrators can also enable a global list. Set batchChanges.agenticBatchChanges.sharing in the experimentalFeatures block of the site configuration:

JSON
{
	"experimentalFeatures": {
		"batchChanges.agenticBatchChanges.sharing": "global"
	}
}
  • link-only (default): users see their own agents. They see other agents only through a share link.
  • global: the list at /batch-change-agents shows the agents of all users on the instance. The list opens with an owner filter set to the viewer. Clear the filter to see all owners.

With global, owners select who can find each agent in the share popover, under Who can find this agent:

  • Anyone on this instance lists the agent for all users who can use Agentic Batch Changes.
  • Only people with the link removes the agent from the global list. The share link continues to work.

The site setting is the upper limit. An agent the owner has not changed follows the site setting. If an administrator sets the setting back to link-only, all agents leave the global list immediately, and owners cannot select Anyone on this instance until the setting is global again.

What a viewer sees

A viewer who can open an agent sees the full transcript: messages, tool calls, and Deep Search results. This follows the model of Deep Search conversation sharing: the person who shares is responsible for the audience. With global, all users with access to Agentic Batch Changes can read all listed transcripts. Consider this before you enable global.

Workspaces, changesets, and diffs keep the repository permissions of Batch Changes. A workspace in a repository the viewer cannot read shows as Hidden repository, without the repository name, the diff, or the changeset details.

A viewer who is not the owner cannot act on the agent.

Agents of deleted users stay in the list, with Deleted user as the owner. An administrator can hand them over to another user. See also Access control for Batch Changes.

Code hosts

The agent publishes through Batch Changes using your configured Batch Changes credentials. Reacting to CI failures and merge conflicts depends on what the code host reports back to Sourcegraph.

Fork enforcement, rollout windows, commit signing, and branch auto-deletion apply unchanged.

Executors

Make sure code host connections are configured for the repositories users want the agent to search and modify.

All code-modifying work runs on executors:

  • Sourcegraph Cloud customers have managed executors with no additional setup required.
  • Self-hosted customers need executors deployed and registered against both the batches and batches-hooks queues, running a version that matches the instance. Without an executor on batches-hooks, batch changes can execute and publish, but CI and merge-conflict hook automations never run.

Billing

Agentic Batch Changes is billed per merged changeset. A changeset counts once it merges, whether it was merged on the code host or in Sourcegraph. Changesets that are closed or never merged are not billed, and model usage by the agent and its coding agent steps is not billed separately.

Subscription admins can find the current rates and consumption on the Credits page in Enterprise Portal.

When the subscription's credits don't cover another merged changeset, the agent can't publish new changesets. Changesets that are already published can still be merged.

The agent's Deep Search research consumes credits at the Deep Search rate.

Deep Search

Before drafting a plan, the agent researches with Deep Search, which is billed at its own rate.

The agent is built to research deliberately rather than repeatedly:

  • It starts with one focused research request covering the repositories, patterns, and edge cases it needs, instead of running a search for each repository.
  • Once Deep Search identifies an exact repository and path, it reads those files directly instead of starting another search.
  • It reuses an existing Deep Search when you link to one in your prompt.
  • It stops researching and drafts the plan once it has enough information to proceed.

Mechanical, well-scoped changes often need no Deep Search at all. Research resumes when a change requires judgment, such as amending a plan after your feedback, working through a complicated scenario, or re-checking the codebase for an agentic batch change that has been open for a long time.

You can shape this behavior with guidance if your team wants the agent to research more or less aggressively. Subscription admins can view Deep Search consumption on the Credits page in Enterprise Portal.

Web search

Web search is enabled by default for the coordinating agent and its coding agents. To disable it for both, set batchChanges.disableAgentWebSearch to true in advanced configuration.

This setting disables web search tools. It does not block outbound network access from executor containers, including commands run by scripts or coding agents. Restrict that access separately through your executor network policy.

Images

Steps run in container images the agent picks, preferring small public images that already carry the needed tools. You can restrict where images come from with batchChanges.containerRegistryAllowlist or batchChanges.containerRegistryDenylist in advanced configuration; the two are mutually exclusive, and an empty list allows every registry.

When no public image fits, the agent can build one on the fly and reuse it across the batch change. Custom-built images are hosted directly in Sourcegraph. Image building is available on Sourcegraph Cloud by default and requires additional setup on self-hosted instances.

Pull request attribution

Agentic Batch Changes link generated changesets back to their agent conversation in both the changeset description and commit message by default. Administrators can configure pull request attribution to keep this link out of descriptions that may trigger unwanted code host notifications.
