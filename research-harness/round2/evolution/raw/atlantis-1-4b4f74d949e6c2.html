Atlantis v0.49.0

v0.49.0 is a breaking release, for three reasons:

  1. The Docker images no longer include Terraform or OpenTofu. This was announced in v0.48.0.
  2. 12 security advisories are fixed here, and several of those fixes change behavior that existing setups may rely on.
  3. v0.47.1 shipped a breaking change without saying so: the shell-injection fix in #6792. It is listed below so anyone upgrading from v0.47.0 or earlier sees it.

Every behavior change is also documented, in a Behavior change note, on the docs page where you would look for that setting. Read Breaking changes before you upgrade.

Upgrade checklist

  • Docker images: set --default-tf-version (and --default-tf-distribution opentofu if you use OpenTofu) so Atlantis downloads the binary. If downloads are blocked, mount or copy a binary into the image instead. The image no longer ships one.
  • Upgrading from v0.47.0 or earlier: check workspace names and comment arguments against the v0.47.1 changes below.
  • GitHub / GHES: make sure --gh-hostname matches the host in your repositories' clone URLs. Webhooks whose clone URL is on a different host are now rejected.
  • Server-side repo config: if repos use allow_custom_workflows: true together with allowed_workflows, check that every project's workflow is in the allow-list. Repo configs that used to pass can now be rejected.
  • Project dirs: make sure no project dir is a symlink to somewhere outside the repository.
  • Comment commands: tell users that -out, -generate-config-out, -state, -state-out and -backup are now blocked after --, and that --blocked-extra-args can no longer unblock anything.
  • Comment -var-file: the allowlist now applies to apply, import and state rm as well as plan. Paths containing .. are refused, and so are repo symlinks that point outside the repository and the allowlist.
  • state rm: if state is in --allow-commands, state rm now has to meet the project's apply_requirements and import_requirements.
  • API: if --api-secret is set, send X-Atlantis-Token on GET /api/locks. Check that /api/plan and /api/apply callers send clean, repo-relative paths[].directory values with no leading / and no globs.
  • Approvals (GitHub, Gitea): apply_requirements: [approved] now uses each reviewer's latest review. On Gitea, dismissed and stale approvals no longer count, and any push that changes the diff makes approvals stale.
  • Apply: plans recorded by v0.49.0 are bound to a hash. A plan file that changes between plan and apply is rejected and has to be re-planned.

Breaking changes

Docker images

The Docker images no longer include Terraform or OpenTofu

  • What changed: the latest, vX.Y.Z and vX.Y.Z-debian images no longer bundle Terraform or OpenTofu binaries, and they set no default Terraform version. This was announced in the v0.48.0 release notes. The -alpine-slim and -debian-slim images from v0.48.0 were the intermediate step toward this and are no longer published. If you pinned one, switch to the unsuffixed, -alpine or -debian tag, which now contain the same thing. If you build the image yourself, use --target alpine or --target debian; the -slim targets are gone.
  • Why: every advisory against any bundled Terraform or OpenTofu release showed up in scans of the Atlantis image, whether or not you used that version. Atlantis can't own the security lifecycle of those third-party binaries.
  • Who is affected: anyone using the published images who relied on the bundled terraform or tofu binary on PATH, or on the version the image used to set by default.
  • How to tell: the server refuses to start with terraform not found in $PATH. Set --default-tf-version ....
  • What to do:
    • Set --default-tf-version (ATLANTIS_DEFAULT_TF_VERSION, or Helm defaultTFVersion) so Atlantis downloads that version at startup. Repos can still pin their own version with terraform_version.
    • For OpenTofu, also set --default-tf-distribution opentofu (Helm defaultTFDistribution).
    • If the server can't reach the release hosts, put a binary on PATH yourself: mount one, or build FROM ghcr.io/runatlantis/atlantis and copy one in. Set --tf-download=false so Atlantis uses it and doesn't try to download.
    • See Deployment: image variants.

Carried over from v0.47.1 (#6792)

v0.47.1 fixed a shell-injection vulnerability (GHSA-rjh2-4xgw-p2hj) and changed behavior along the way, but its release notes didn't call that a breaking change. If you are upgrading from v0.47.0 or earlier, these apply to you.

Terraform and conftest commands no longer run through a shell

  • What changed: Atlantis used to build Terraform and conftest command lines as strings and run them with sh -c. Commands now run as argument vectors.
    • Each extra_args entry is passed as exactly one argument. Shell operators (;, &&, |, redirections), globbing and word splitting no longer apply.
    • Environment references such as $WORKSPACE and $DIR are still expanded in operator-configured extra_args, but no longer in arguments typed in a PR comment after --.
    • For conftest, a policy set path and each extra_args entry are still split on whitespace. Quote a path that contains a space.
  • Who is affected:
    • Workflows whose extra_args relied on shell behavior, for example two flags in one entry, a pipe, a redirection or a glob.
    • Users who passed $VAR references in comment arguments and expected them to expand.
  • What to do: split multi-flag entries into one argument per entry. Move anything that needs a shell into a run step, which still runs with a shell by design.

Workspace names are validated everywhere

  • What changed: workspace names from repo atlantis.yaml, the -w comment flag, the Terraform Cloud workspace read from HCL, and the API are validated. A name can't contain /, \, .., $, whitespace or control characters, can't be ., and can't start with - or ~.
  • Who is affected: projects or comments using such names. A name containing $ never worked, because the shell expanded it.
  • How to tell: repo config validation fails under the workspace key, or the comment is rejected with the offending value and a reason such as cannot contain '/' or '\'.
  • What to do: rename the workspace to one without those characters.

Server-side repo config

allowed_workflows is now checked for every project (GHSA-56q6-8vmp-v2qm)

  • What changed: with allow_custom_workflows: true, a bug stopped the allowed_workflows check at the first project that used a repo-local workflow. Projects after that one were never checked. Now every project is checked.
  • Who is affected: repos with allow_custom_workflows: true, allowed_overrides: [workflow] and a non-empty allowed_workflows, whose atlantis.yaml has a later project naming a server-side workflow that is not in allowed_workflows.
  • How to tell: the repo config fails validation with workflow '<name>' is not allowed for this repo.
  • What to do: add the workflow to the repo's allowed_workflows in the server-side config, or change the project to use an allowed workflow.

A project dir that symlinks outside the repository is rejected (GHSA-9q39-mgw7-5789)

  • What changed: Atlantis now follows symlinks before checking that a project directory is inside the clone. Before, the check only looked at the path as written.
  • Who is affected: repos whose project dir (or a parent directory in its path) is a symlink pointing outside the clone. That includes absolute targets and ../ targets that leave the repository. Symlinks that stay inside the repository (for example dir -> modules/x) still work.
  • How to tell: plan, apply, import and state commands fail with project path traversal detected: .... A path that cannot be resolved for any other reason (for example a file where a directory is expected) now fails with resolving project path: .... Before, Atlantis ignored that case.
  • What to do: replace the symlink with a real directory inside the repository, or point it at a target inside the repository.
  • Also changed: a broken dir symlink keeps the existing dir "<dir>" does not exist error. If anything other than a regular file (for example a symlink) sits at the plan file path inside the project directory, Atlantis deletes it before planning.

Comment commands

More Terraform flags are blocked after --, and --blocked-extra-args now adds to the list instead of replacing it (GHSA-chm7-fjpm-927x)

  • What changed:
    • These flags are now always blocked in comment extra args: -chdir, -plugin-dir, -out, -generate-config-out, -state, -state-out, -backup. Before, only -chdir and -plugin-dir were blocked.
    • Flags are matched by name. One entry blocks both the - and -- spellings and the =value form.
    • --blocked-extra-args now adds to the built-in list. Before, setting it replaced the defaults, so an operator could unblock -chdir or -plugin-dir that way. That is no longer possible.

    • Users who pass any of these flags in comments. Watch for atlantis plan -- -generate-config-out=..., which some teams use to generate config for import blocks.

    • Users who pass Terraform's own -state or -backup to atlantis state rm in comments. Those are blocked too.

Highlights

Emergency security release for the eMudhra intermediate CA key compromise. The private keys of eight eMudhra (emSign) intermediate certificates were compromised; some of those intermediates are cross-signed by a root that every trust store includes. We recommend all users upgrade.

  • Go 1.27.3: Atlantis is now built with go1.27.3, whose crypto/x509 rejects any certificate chain containing the eight compromised keys (CVE-2026-111943). Go does not check revocation, so Atlantis v0.48.1 and earlier, built with go1.27.1, would accept a certificate issued with those keys for any host, including the VCS APIs Atlantis sends credentials to. go1.27.3 also includes the standard library fixes from go1.27.2.
  • Trust store update in the images: ca-certificates is updated to Alpine 20261020-r0 and Debian 20250419+deb13u1. Both remove emSign ECC Root CA - G3, and Debian also removes the Comodo AAA Services root that cross-signed some of the affected intermediates. This covers the other TLS clients in the image (git, curl, Terraform/OpenTofu and conftest).
  • Runtime image refresh: Debian curl 8.14.1-2+deb13u7 and openssl 3.5.7-1~deb13u3 security pins, Alpine 3.24.2, Terraform 1.16.5, conftest 0.70.1.
  • Dependency security updates: golang.org/x/net v0.60.0 and vite v8.3.3.

If you build Atlantis yourself, rebuild with go1.27.3 or go1.26.10 or later. The terraform, tofu and conftest binaries are built by their own projects; update them when their releases with the Go fix are available.

Atlantis v0.48.0

### Terraform and OpenTofu Binaries Removed from Debian and Alpine Images

Starting with Atlantis v0.49.0, the Debian- and Alpine-based Docker images will no longer include bundled Terraform or OpenTofu binaries.

Users can continue to use Atlantis' automatic binary download functionality to fetch and use the Terraform or OpenTofu versions required by their workflows.

This change allows the Atlantis project to focus its security and maintenance efforts on the Atlantis application and its container images, rather than taking responsibility for the security lifecycle, vulnerability management, and distribution of third-party Terraform and OpenTofu binaries.

Users who require pre-installed binaries can continue to build custom Atlantis images based on the official images.

Highlights

  • Safer plan/apply lifecycle. Atlantis now hashes the loaded apply plan, persists plan results before reporting success, and applies the verified managed-plan snapshot.
  • New slim container images. Alpine and Debian slim images are available without bundled Terraform or OpenTofu, for deployments that provide their own tooling.
  • Terraform and runtime compatibility. End-of-life Terraform versions without security support were removed from the standard images. The bundled versions, Debian and Alpine bases, Go toolchain, OpenTofu, Conftest, and Git LFS were refreshed.
  • Operational and security hardening. GitLab webhook tokens are omitted from errors, and drainer and workflow-hook status handling is more reliable. The GHSA-rjh2-4xgw-p2hj shell-injection fix is retained from the mainline history; it was already shipped in v0.47.1 and is not presented as new here.
  • Documentation and localization. Spanish documentation and translation infrastructure were expanded.

Runtime and compatibility changes

  • Standard images now use Terraform 1.16.3 and 1.15.9, with older unsupported Terraform versions removed.
  • Alpine and Debian base images were updated, along with the Go 1.27.1 runtime/toolchain, OpenTofu 1.12.6, Conftest 0.70.0, and Git LFS 3.8.0.
  • New alpine-slim and debian-slim image targets do not bundle Terraform or OpenTofu.
