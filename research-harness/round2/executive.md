# 从 code agent 团队的角度，下一步值得做什么

**建议保留现有 code agent 的执行能力，把新增研发投入放在两处：协助负责人处理一批仓库的例外，以及独立决定一次自动修改何时可以交付。** 前者把重复的人工接管整理为可复测样本，供后续提出候选；后者保留独立否决与回滚的权力。两项可以各自试验，即使最终更换执行器，任务、验收和接管数据依然可用。

### 产业的前沿已经走到了哪一步

|工作|已有产品能交付什么|你们还有什么值得验证|
|---|---|---|
|从单仓 issue 到候选变更|GitHub Copilot cloud agent、GitLab Duo、Devin 等能在各自权限和宿主条件下接单，生成可审的候选。已有成熟入口，独立开发一个“替用户开 PR”的入口很难单独证明价值。|交给一批服务后，谁来处理共同失败、判断未迁完的消费者、确认旧分支和在途动作？可用现有执行器比较这部分净人工投入。|
|从任务失败到下一版 harness|研究系统可从失败轨迹改提示、记忆或工具。部分商业平台已能在同一产品内支持标注、候选评估与提示版本切换。发布门禁、外部副作用与补偿归属要逐项查证。|团队自己积累下来的“什么时候该停、谁接手、怎样验明修好”，能否形成下一批未见任务的独立测验，持续拒绝有严重回归的新版本？|
|从通知人到有效接管|工作流引擎已有持久化、寻址、重试；商业产品也提供审批与协作界面。|审批绑定对象和版本、外部动作有幂等键、换人后能看清已发生的副作用。双引擎的实验证明，缺少这些约束时恢复流程仍可造成重复写入。|
|从个人产量到组织收益|PR、接受率、评审、部署等事件可以收集；不同研究已经观察到工作从编码移向评审和交付。|是否真的缩短本组织的交付周期，需看全部合格任务、人的实际分钟及上线质量。提供能改变下一步动作的证据，比多做一个席位活跃看板更接近产品价值。|

### 两项已推翻或收窄的判断

**第一轮给 CI 分诊排了无条件第一，现在应按工作清单选。** Airbnb 的公开迁移留下了早期快速进展、难例重试和人工接管的可追踪记录。现有规则在真实代码快照上已能完成不少机械改写，项目组合甚至会改变哪种工具覆盖更高。若客户有到期 API 和可枚举的仓库，先拿这个场景；如果没有规模化迁移，再看 CI 中是否有重复、高频、能独立复现的失败。避免把一个工具做出了补丁解释成部门工作已经结束。[Airbnb 工程记录](https://airbnb.tech/infrastructure/accelerating-large-scale-test-migration-with-llms/) · [公开迁移研究](https://research.google/blog/accelerating-code-migrations-with-ai/)

**“多个执行器各有所长”在真实逐题记录中成立，简单路由却未兑现这笔收益。** 在同模型修订的五次公开历史提交里，500 题有 358 题至少被一个系统解出，最佳单次提交为 265 题。用过去仓内成绩选执行器，20 次固定切分里有 19 次输给训练总体选优。它给 auto harness 团队一个清晰的试验：让候选规则先在未见任务上击败单一强基线，再谈上线或增加路由复杂性。公开老题与真实企业工单之间还有分布差异。[官方提交原件](https://github.com/SWE-bench/experiments/tree/40f164d5b8f1d249bf95a6df8b74b577fd8e519d/evaluation/verified)

### 有哪些证据会改变产品设计

- **给对人、问对问题、交付正确结果需要分开验收。** SWE-CoWork 中给两种模型完整需求，节点通过率涨约 16 个百分点，整项通过率都维持原水平。在真实公开 PR 上，满 24 小时无决定、无终态的 37,882 件中，16,502 件后来未见正式决定便合并或关闭。对组织级产品，可以把“提醒谁”与“哪个外部条件被解决”分别计量。一个是模拟实验，一个是公共事件回放，均没有测客户工时。[协作 benchmark 及对账](cowork/result.md) · [提醒时机](supervision/result.md)
- **CI 的历史预测值要经过派发时刻检验。** OpenStack 资料中的一项强预测量依赖本次重跑结束时出现的 job 名单。把请求连接到真实调度记录后发现，同 patch 甚至可能关联到数日后另一事件。OpenStack 的 70,740 个留出请求中，少派 5,061 次、错挡 430 次本可转绿；GitHub Actions 的 1,472 个留出记录中分别为 83 次和 43 次，其中 41 个误挡来自同一仓。按“少派次数 ÷ 错挡次数”，若一次错挡的损失超过约 11.77 或 1.93 次重跑的成本，相应策略在该简化口径下不再划算。首发可以给证据、影子建议和覆盖入口；自动阻止要逐客户、逐仓验证。[作业可得性审计](ci-availability/result.md) · [跨生态](ci-cross/result.md)
- **成熟团队已有可借的边界。** Stripe 在完整 CI 的再试之后把分支交人，Ramp 将重复告警挂回原修复，并将候选与已合并变更的差异交给独立评审。可以沿现有平台的 CI、评审和发布接口做接管层；真实的差异化要在反复失败、多人交接和验证还未结束时显现。[四个现场](factories/result.md) · [五组互操作规范](interoperability/result.md)

### 平台团队和业务团队各持有什么决策权

**先给既有工具一次赢的机会。** Python 的 Renovate 实跑中，一个被标为非 breaking 的依赖候选令旧消费方的 39 个框架测试全部失效。换到 React/Testing Library 的九格矩阵，严格 npm peer 检查在安装时已提前挡住所有三个被本次运行证实的故障，允许的四格全部通过。本团队应针对现成工具仍会放行的难例验证新增价值。若错误组合在安装时已经被挡住，产品的正确动作可能只是解释约束、提出可逐步升级的中间版本。[Renovate 实跑](dependency-bot/result.md) · [JavaScript 对照](js-compat/result.md)

平台团队维护执行器适配、事件重放、证据存储、候选评估与成本核算。服务团队定义能从外部观察的验收、依赖与质量底线；维护人对需要业务判断的例外拍板。评估候选版本的人事先锁住留出集与判据，产品负责人决定何时扩大流量。设计时让这些角色即使不在同一工具里，也能以同一工单、内容版本和交付对象核对彼此的决定。

**第一份内部试验应能交出一张有限清单。** 写明起点时哪些工作需要完成、现有流程会怎么做、各仓或各任务的 owner、必须看到的独立证据和截止日期。先用现有规则干跑，再请服务负责人指出哪些剩余难例确实卡在工程劳动上。如果拖期来自消费者未排期或业务决策尚未作出，继续优化执行器难以提前交付。试验结束时逐项标已验收、失败、转人工、已放弃、仍未决，并附上实际人时和计算成本。

### 组织层面已有谁能做，哪里仍需自研

DX、Jellyfish、LinearB 已分别把软件实体检查、组织调查与工程事件、等待评审的 PR 做成可购买的产品。团队若已有这些系统，应先接入其分组、派单与调查能力，把新开发留给真正缺失的能力，例如在执行器、产品负责人和服务负责人之间传递一份可独立验收的例外。不同平台使用的人、PR、事件和时间窗要逐项对齐。Apache DevLake 的 beta13 同一详情面板，用项目自带的五次部署及六起事故，在真实 MySQL 与 PostgreSQL 引擎里分别得到 40% 和 120%。SQL 版本、关联记录和计量单位都属于交付物。[三家组织效能平台](eng-intel-vendors/result.md) · [开源 DevLake 的指标实现](devlake/result.md)

开放实现提供了一个具体的发布边界。本地 MLflow 3.18.0 支持版本与别名，四个独立进程却证实，生产别名回滚后预热的消费者仍可读旧内容；单有提示版本号也锁不住后改的模型配置。应先用已有注册表管理版本，再验证端到端的审批对象和实际生效时刻。真实开发者试验还显示，愿意报名、愿意在禁用 AI 时做的任务，与实际进入工时回归的任务并非同一集合。内部试点要先登记所有可办的工作，持续记录由谁选择、谁拒绝、谁收尾。[注册表实测](promotion-replay/result.md) · [试验进入差异](selection-effect/result.md)
