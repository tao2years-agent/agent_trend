# 哪个仓需要先升：两条跨项目兼容链

这是一项按已知向后不兼容事件选样的机制复演，不能估计升级失败率。选择 Flask–Werkzeug 和 Starlette–HTTPX 两条由不同维护者发布的生态依赖，均有公开证据表明至少一个旧客户端在依赖变化后会出问题。运行前已知 Flask 2.2.2 与 Werkzeug 3.0.0 的导入问题，以及 Starlette 0.37.2 移除了 HTTPX 测试客户端的旧参数。本试验追问同一对版本变更，在安装元数据、实际导入、请求级契约和上游测试四种验收上是否给出同一结论，且先升哪一边可避免中间状态失败。

选择 Flask 2.2.2 / 2.3.3 / 3.0.0 × Werkzeug 2.2.3 / 2.3.8 / 3.0.0，Starlette 0.36.3 / 0.37.2 / 0.38.6 × HTTPX 0.26.0 / 0.27.2 / 0.28.1。不顺序只检查升级成功样本，全部 18 个组合都入表。用干净的相同 Python、同一组锁死的支持依赖、只从带 SHA 的官方 PyPI wheel 安装。不允许 pip 自行换掉指定主版本；安装失败保留。记录正常的本地路由调用和测试客户端路径，测试不用真实网络。独立运行发行方上游包中的相关测试文件或有明确来源的选定函数，环境失败另列。若源码测试依赖不可满足则降为运行时探针，不把我们自写的用例叫成上游测试。另记录预告弃用的 warning；比较对 warning 一刀切是否也会拦下仍可工作的组合。对每条生态从起点到目标按一次只升一项画可行路径；中间态不可用时是否需要两边协调，作为先后顺序的证据。
