L37: # flynt - string formatting converter
L38: 
L39: `flynt` is a command line tool to automatically convert a project's Python code from old "%-formatted" and .format(...) strings into Python 3.6+'s "f-strings".
L40: 
L41: F-Strings:
L42: 
L43: > Not only are they more readable, more concise, and less prone to error than other ways of formatting, but they are also faster!
L44: 
L45: ### Installation
L46: 
L47: `pip install flynt`. It requires Python version 3.9+.
L48: ### Usage
L49: 
L50: Flynt will modify the files it runs on. Add your project to version control system before using flynt.
L51: 
L52: To run: `flynt {source_file_or_directory}`
L53: 
L54:   * Given a single file, it will 'f-stringify' it: replace all applicable string formatting in this file (file will be modified).
L55:   * Given a folder, it will search the folder recursively and f-stringify all the .py files it finds. It skips some hard-coded folder names: `blacklist = {'.tox', 'venv', 'site-packages', '.eggs'}`.
L56: It turns the code it runs on into Python 3.6+, since 3.6 is when "f-strings" were introduced.

L139: ### Pre-commit hook
L140: 
L141: To make sure all formatted strings are always converted to f-strings, you can add flynt to your 【10†pre-commit†www.pre-commit.com】 hooks.
L142: 
L143: Add a new section to `.pre-commit-config.yaml`:
L144: 
L145:     `-   repo: https://github.com/ikamensh/flynt/
L146:         rev: ''
L147:         hooks:
L148:         -   id: flynt
L149:     `
L150: 
L151: This will run flynt on all modified files before committing.
L152: 
L153: You can skip conversion of certain lines by adding `# noqa [: anything else] flynt [anything else]` or `# flynt: skip`
L154: ### Configuration files
L155: 
L156: Since v0.71 flynt can be configured using `pyproject.toml` file on a per-project basis. Use same arguments as in CLI, and add them to `[tool.flynt]` section. CLI arguments takes precedence over the config file. It can also be configured globally with a toml file located in `~/.config/flynt.toml` on Unix / `~/.flynt.toml` on Windows.
L157: ### About
L158: 
L159: Read up on f-strings here:
L160: 
L161:   * 【11†https://realpython.com/python-f-strings/†realpython.com】
L162:   * 【12†https://www.python.org/dev/peps/pep-0498/†www.python.org】
L163: 
L164: After obsessively refactoring a project at work, and not even covering 50% of f-string candidates, I realized there was some place for automation. Also it was very interesting to work with ast module.
L165: ### Dangers of conversion
L166: 
L167: It is not guaranteed that formatted strings will be exactly the same as before conversion.
L168: 
L169: `'%s' % var` is converted to `f'{var}'`. There is a case when this will behave different from the original - if var is a tuple of one element. In this case, %s displays the element, and f-string displays the tuple. Example:
L170: 
L171:     `foo = (1,)
L172:     print('%s' % foo) # prints '1'
L173:     print(f'{foo}')   # prints '(1,)'
L174:     `
L175: Furthermore, some arguments cause formatting of strings to throw exceptions. One example where f-strings are inconsistent with previous formatting is %d vs {:d} - new format no longer accepts floats. While most cases are covered by taking the formatting specifiers to the f-strings format, the precise exception behaviour might differ as well. Make sure you have sufficient test coverage.
