# MLflow 实测：回滚了 production，谁还在用旧版本？

**真实回滚成功，但已缓存的另一个进程仍拿到回滚前的提示。** 写进程将 production 从 v2 改回 v1 后，它自己从注册表读到 v1；另一个已预热的进程按默认配置仍返回 v2，同一进程禁用缓存才读到 v1。此前已取出的 v2 对象仍能格式化为旧文案。关闭原有三个工作进程后，第四个新进程从同一数据库读出 production=v1；独立只读 SQL 也返回 v1。实验还发现：未绑定数字版本的候选审批可指向另一版本；即使绑定数字版本和模板，公开 API 仍可改变模型配置。版本注册、审批执行、消费者切换分别需要验收。[逐步事件与读取值](timeline.csv) · [重开 SQLite 的证据](reopened-sqlite.json)

MLflow 的公开 Prompt Registry 支持按名字创建多版模板、用逻辑名称发布、按版本号取回历史版本。对组织采购更重要的是同一次改指针能否绑定被评估的内容，以及回滚后谁已经读到了新版。这份本地复算使用开放发行包与真实 SQLite，单设一项工程参照，既不加入研发采购 35 项，也不加入提示评估采购原有 6 项。[试验协议](protocol.md) · [固定发行包](sources.json)

## 核验对象

- 产品操作使用官方 Python API：register_prompt、load_prompt、set_prompt_alias、set_prompt_model_config。数据库快照仅由只读 SQLite 查询生成；除官方库迁移及写操作外，试验代码没有向这些表发 SQL 写入。文案和应用时钟为研究夹具，人员审批、签名、身份授权及防重账本均未作为 MLflow 原生功能评分。
- 发布面以 Apache-2.0 许可的开源 MLflow 3.18.0 为准。PyPI 完整包于 2026-11-03 UTC 发布，三份同版官方 wheel 已固化。实验采用笔记本上的本地 SQL store，未启动公网服务、商业控制台或模型端点。下文的旧值、过期和回滚都指这一特定接口与持久层。[官方发行记录](https://pypi.org/project/mlflow/3.18.0/) · [官方提示注册表](https://mlflow.org/docs/latest/genai/prompt-registry/)

## 实际发生了什么

全程用 4 个独立 SDK 工作者、同一真实 SQL 数据库。51 步包括注册、按别名或版本读取、格式化已取对象及写指针，50 步成功，1 步为有意的不存在版本。另有 9 次本地夹具的审批校验，不能计作产品拒绝。六次只读 SQL 快照均见到完整的 v1、v2、v3；四个工作者无 socket 连接尝试、均正常退出，也没有模型调用。[原始观测](observations.json) · [验收校验](validation.json)

| 提问 | 怎么试 | 读出的实际值或失败条件 |
|---|---|---|
| 批的是哪个候选？ | 步 4–11，production=v1、candidate=v2；记录同意 v2 后让 candidate 移到 v3，执行时按浮动 candidate 重解析。 | 宽松业务逻辑确实把 production 改成 v3，输出变为 `Reminder: Friday planning.`。辅助校验比较批准的数字和内容摘要，能在这条顺序路径发现变化。错误绑定来自调用方，不是注册表把同一个数字版本取错。|
| 已经过期的审批能挡住写入吗？ | 夹具的逻辑当前时间为 100，票据在 99 过期；步 15–16 再以已获写入权限的客户端只提交 production、数字 2。 | 夹具拒绝，产品 setter 根本不接收这张票且成功写入 v2。相反，给同一 setter 一个不存在的 v999，返回 `RESOURCE_DOES_NOT_EXIST`，production 仍为 v2（步 29–30）。存在性由产品原生检查，票据有效期由调用侧负责。|
| 不同读者何时能看到提升？ | 步 18–32，读进程先默认加载并保留 v1，写进程改成 v2。分别试默认、跳过缓存、全新进程及真实 TTL。 | 写进程立即见 v2；已预热的外部读进程仍见 v1，TTL=0 见 v2，再次默认仍返回既有缓存 v1；新进程见 v2。首次缓存后 61.015 秒再读见 v2，当初持有的对象仍能格式化 v1。默认期限为 60 秒，此试验没有测量期间每一毫秒的传播曲线。|
| 数字版本能锁住评估时的配置吗？ | 步 26–28，对 v2 调用 `set_prompt_model_config`，将 temperature 从 0.1 改为 0.8。 | v2 与模板摘要完全相同；模型配置和完整内容摘要已有变化。六次 SQL 快照保留同一模板文本，末次 SQL 显示 v2=0.8，其他两个版本仍为 0.1。没有请求模型，因此没有测输出质量变化。|
| 旧发布决定能覆盖新决定吗？ | 步 33–39，两个进程都看到 production=v1，各校验自己的候选。B 写 v3；A 此时显式重读可见 v3，再按此前的判断调用原生 setter 写 v2。 | A 的写入成功，SQL 变为 v2。SQLite 的每笔写都完成，但单独的“先验证，稍后写”不能拒绝过时前置值。这里固定了一种执行交错，没有测冲突发生率。|
| 回滚到相同数字会怎样？ | 步 40–49，production 回到 v1；用已用过且尚未过期的旧票再比较数字前置值和内容摘要。随后使用新票，提升至 v2 再回滚。 | 单看数字和摘要的夹具再次放行，同一性检查遇到“v1→其他→v1”就分不清两次发布。夹具额外检查已使用票号时拒绝；该集合没有生产持久性。最后回滚后，另一进程默认仍见 v2，TTL=0 见 v1，已持有的 v2 仍输出 `Next meeting: Friday planning.`。|
| 进程退出后事实还在吗？ | 步 50–51，关闭前三个进程，第四个使用相同 SQLite 启动，再按别名和显式数字取回。 | production=v1，v2 仍可显式取回。独立 SQLite 完整性检查为 ok、外键错误 0。只共享涉及合成文案的字段投影及完整数据库指纹，避免复制宿主的本地路径。|

## 运行结果对应的源码

公开 `set_prompt_alias(name, alias, version)` 只接收提示名、别名与目标版本。跟踪客户端第 1288 行开始的方法先验证该版本存在，再调用 store；写成功后删除当前进程中该别名的缓存。SQLite 使用的默认 adapter 将操作交给注册模型别名；SQLAlchemy store 在写事务内取到合法目标版本并 merge 一条别名行。单次写的事务性成立，但方法签名没有上一次 production 所指版本、审批编号或失效时间可以一起比较。这一判断限定在此次运行的开源 SQL 路径。[公开入口](raw/mlflow__genai__prompts____init__.py.txt) · [SDK 缓存失效逻辑](raw/mlflow__tracking__client.py.txt) · [SqlalchemyStore](raw/mlflow__store__model_registry__sqlalchemy_store.py.txt)

同一版本的某些内容仍可维护。公开 `set_prompt_model_config` 校验字典，然后写入指定版本的模型配置 tag；提示模板与模型配置是不同字段。审批若只绑定数字和模板文本，将遗漏这个 API 可改的配置。研究夹具另外计算了提示名、数字版本、模板和模型配置的规范化 JSON 摘要，未把该自选摘要说成产品签名。[公开模型配置 API](raw/mlflow__genai__prompts____init__.py.txt) · [PromptVersion 的字段](raw/mlflow__entities__model_registry__prompt_version.py.txt)

## 这会怎样改变选型

如果采购目标是让发布者精准指定一个已有版本、给新消费者一个可以更新的生产入口，这个层次可以用开源注册表交付。若采购目标是“只有本次审批的候选才能替换特定现行版本”，采购验收还得要求一个受控写入口：审批记录绑定目标版本及实际影响行为的配置、预期现行发布代数、到期时间；对票据消费和生产指针写入使用共享事务或等价的原子条件。单次 SDK 写在事务中，不代表应用先查再写也是同一事务。验收还应单列多进程缓存最长可见延迟、紧急回滚时读取策略，以及已经拿到旧内容的任务怎样处理。

本研究的“在途”仅是另一个进程已经取得的真实 PromptVersion 对象，再调用真实 format；未运行模型、消息投递或外部工单，不据此推断这些副作用可以补偿。夹具检查使用合成逻辑时钟和进程内已消费票号集合，不是生产签名、授权服务或可并发的防重账本。托管控制台、企业角色策略和其他 MLflow 后端未测，不能从这个 SQL setter 推断所有产品路径均无审批。

复现所用的 91 个 Windows wheel 共 161,850,218 字节，全部 SHA-256 已锁定。六个关键模块的安装字节与固定发行包源码相同。可复跑命令见[试验约定](protocol.md)，持久层可独立用[只读核验脚本](sqlcheck.py)检查。
