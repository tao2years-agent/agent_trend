# 谁能修改 harness，谁决定它值得保留？

**在同一模型外改写执行程序，已经有两种可读源码的研究实现。** Stanford 的 Meta-Harness 会提出新的候选 agent 程序，并分别记录每项任务和总体的领先者。AHE 会用执行轨迹定位问题，在可编辑的工作区修改提示、工具或中间件，再按实测结果做下一轮选择。两者都能产生新版本；要把其中某个版本发布给工程团队，还需明确在哪组未见任务上验证、严重错误能否否决，以及谁有权限切换线上版本。

本次阅读作者的两个固定提交，保存 21 个完整文件，选取四个函数做 11 组合成输入的局部运行。下文将论文作者报告的结果、源码控制流、局部实验和产品建议分开。没有调用模型、启动 Harbor、连接集群、运行真实 benchmark 或发布任何候选。[源码索引与固定修订](sources.md) · [本次探针及结果](probe-results.json)

## Meta-Harness：同一个“前沿”文件有两种领先者

案例采用官方仓库 2026-11-05 提交 f805ad3。仓库并列提供 Terminal-Bench 2、文本分类及 experimental Harbor 控制器，它们是不同实现路径，特别是训练与验证的隔离方式不同。

|问题|Terminal-Bench 2 参考实现的证据|
|---|---|
|可修改什么|从 KIRA 基线出发，proposer 生成 agents/ 下可 import 的候选 agent 类。候选可读先前运行的代码和反馈；入口先验证候选可导入，再可选择用单任务单 trial 做 smoke 检查，随后进入 Harbor 计分。可导入或 smoke 成功只能说明候选能起步。|
|模型、预算和分母|参考 CLI 缺省迭代 5 轮、每题搜索 2 个 trial、proposer timeout 2,400 秒。代码所选 full 任务集有 89 题，README 另建议先以较小集合验证。已有 trial 目录若缺结果、无 verifier 奖励或 JSON 坏则计 0。整个 trial 目录未出现时不进入解析；与期望次数不同会打印警告。汇总把发生的所有 trial 平铺，奖励大于 0 算通过；每题 trial 不等时不能当作逐题平均。|
|如何晋级|update_frontier 分别处理每题通过率和总体通过率，均要求严格大于旧值；平局保留当前记录。某候选可以给一个薄弱题型刷新记录，同时总体冠军仍是旧版。这套前沿记录没有决定将代码推向生产。|
|读写边界|候选的预期写入目标、运行目录和允许的工具，在 README、skill 与 proposer wrapper 中可见。wrapper 本身开放读写和 shell 工具；目录约定或提示文字单独不能证明宿主实施文件 ACL。本研究未使用该执行入口。另一路 experimental/harbor_meta_harness/controller.py 会检查禁用的 benchmark 引用、初步语法、AgentHarness 基类及 async run 形状，对候选源码求 SHA-256，再分别运行子任务。段中的静态检查不是 TB2 参考实现已经执行的前置条件。|
|能否重放|各次 Harbor 作业、候选名称与 import 路径、结果日志和 frontier 文件能追溯选择；外部模型服务、容器和工具版本仍须另存。可选 full-eval 会对非基线赢家用 5 个 trial 重跑同一套完整 TB2；它检验重复抽样的稳定性，无法替代新任务留出。|

上述控制流见 Meta 的 reference_examples/terminal_bench_2/meta_harness.py L210–272、L373–393、L459–483、L858–892 与 CLI 参数。另一条文本分类路径在 config.yaml 明确列出 train/val/test 和 seed，并在 finalize_run 中选择基线、验证集 Pareto 候选及逐数据集赢家做 test。读取到 complete 状态时跳过再次评估，仅展示既有 test 结果。测试数据公开且可在宿主中读取，能否做到对 proposer 隐藏还取决于部署。不要把文本分类的留出结论移植到 TB2。[核对文件与本地快照](sources.md)

## AHE：最佳分数、当轮赢家和回滚建议分别产生

案例采用 2026-10-30 提交 182ea06。主循环先评估当前工作区，保存 trial、轨迹和逐任务结果；比较上轮差分，将失败证据交给进化代理，在下一轮观察修改效果。配置和提示列出系统提示、工具描述/实现、中间件、技能、子代理和长期记忆等可修改对象，也明确 runs/ 供读、评测器与 tracer 不在写入范围。证据证明存在这些约束文本，不能替代对真实宿主权限的测试。

- **训练和验收对象。** 发布配置的父子 YAML 把 code agent 设为 GPT-5.4，Harbor 每题两次 rollout；子配置指向 89 题的 Terminal-Bench 2 long-time 集并覆盖并发度。每轮都会看到相同任务上的执行轨迹与差分，不是每轮重抽未见项目。作者 README 报告冻结后迁移到 SWE-bench Verified；base.yaml 中 post_evolve 默认关闭且可另配数据集。不能把论文迁移实验理解为默认每轮的发布门禁。
- **预算。** 基础配置给出 100 轮及目标通过率 0.95；真实实验可覆写。示例中的 100 不是论文实际使用轮数，README 报告的研究运行是 10 轮。基础配置中的作业/总实验时长字段为零，不可用它们宣传固定费用封顶。版本记录还固定了 NexAU 的源码 revision；本地来源覆盖、模型/服务端的变化仍会影响重现。
- **历史最好分数。** update_best_ever（evolve.py L2369 起）只有严格提高通过率才刷新历史记录。主循环分别保存 configuration、每轮开始的工作区快照、任务历史、得分、变更清单和 Git tag。恢复指定 iteration 时若没找到相应快照，会回到当前工作区继续；恢复演练要核对实际 hash。
- **可选 Best-of-N。** base.yaml 默认关闭，配置 n=2。开启后不同候选进入独立工作树，控制器先按 idx 排序，挑有评测作业的变体，按通过率优先、异常数次之、平手保留先出现者。候选都无有效作业时保留当前工作区。若有有效评测，但最优候选仍差于输入基线，select_variant_winner 只发警告，调用方随后仍会尝试 adopt_variant_winner。该选择决定下一轮搜索工作区，与历史最佳记录、线上部署是三件事。
- **细粒度回滚。** 主循环 Phase 2.7 在注释中明确 change attribution 先出报告，是否回滚由进化代理判断。单独分发的 skill 回滚指南对 P0 或多项新回归描述了更强的规则；随附 verify_manifest.py 的 evaluate_predictions 实际只用 expected_fixes、at_risk_regressions 和当前 passed/failed 产生 keep/revert/partial。将结果写入 manifest 不等于触发一次成功的 Git 恢复。个别失败是否 *新出现* 还需对照旧版本。

证据定位为 AHE evolve.py L607、L2369、L3321–3344、L3881–3970、L4161–4180、L4265–4282、L4385–4405；配合 configs/base.yaml、两个实验 YAML、evolve_prompt.md 和独立的 verify_manifest.py 阅读。[核对文件与本地快照](sources.md)

## 无模型的局部对照

探针核验源文件原始 SHA-256，通过 Python AST 只提取指定的原版函数体，保留函数上下文所需的标准库对象。Meta 的 frontier 实际写入和读取临时 JSON；AHE 实测只运行选择与打标签函数，没有执行 Git 合并或任何外部工具调用。

|合成场景|实际观察|可用于验收的反例|
|---|---|---|
|Meta 旧版两题各试两次，A 得 2/2、B 得 0/2。新候选 A、B 均得 1/2。|总体各为 50%，总体冠军仍为旧版，B 的记录变成新候选。再引入总体 25% 的候选不会刷新总体；75% 候选才换总体冠军。|逐任务冠军表可展示长处，不宜拼成一个真实在役 agent 的成功率。|
|AHE 基线 80%，两个有效候选 50% 和 60%。|函数记录警告并选 60%。同分 80% 时，异常更少的变体胜出；分数、异常数都相同时，在上层预排序后的较小 idx 留下。|如果组织要求非劣才进入部署，必须独立检查基线，而不是将“本轮赢家”当发布批准。|
|AHE 声明希望修复任务 T，T 通过。另一项列为 at-risk 且失败；对照组改为两项未在风险表列明的失败。|前者得到 revert，后者得到 keep。无观察记录得 partial，目标任务确实失败得 revert。|缺少观察和没有发现回归要分开。在独立门禁里保存旧新结果、覆盖全部严重任务，再判断哪些是新失败。|

四个 Meta、三个 AHE 选择、四个 AHE 清单条件共 11 项；均是选择逻辑的反例和边界测试，数量不代表是否能跨任务自动提高模型表现或组织效率。[可执行探针](probe.py) · [逐条输入、输出和断言](probe-results.json)

## 给研发平台的两条验收线

**给搜索流程**保留一笔探索预算，允许候选暂时低于基线，但禁止搜索器取得线上切换权。**给发布流程**固定旧版、候选、任务族与验收器版本；在隐藏的近期任务上比较同预算净效果，对严重项单独设否决，再做影子运行和版本回退演练。第一条降低盲目调提示的成本；第二条检验此前的失败是否换了一种形式再次流入生产。两个公开实现为前者提供了具体示例，无法代替后一条在企业里的实测。
