# 让工程团队能放心把哪项工作交出去

现有 code agent 可以保留为执行器。接下来值得投资的是三项能单独验收的能力：让一次研发任务从触发走到业务终点，让负责人只在需要判断的例外上介入，让 harness 的每次自动修改都有机会被独立否决。平台团队可以沿这三项能力选第一个场景，无需先重写模型、编辑器或工具调用内核。

## 先看下一季度要完成什么

|组织里观察到的情况|首个试点及对照|推翻这项选择的证据|
|---|---|---|
|有弃用日期，能列出目标仓及 owner，且可逐仓检查旧 API 是否退出|选择一次真实迁移。与现有规则工具＋工程师的做法比较，在同样的剩余难例上测试 agent。按仓分批，在指定发布和观测窗后验收。|主要耗时发生在产品兼容决策、下游未排期；干跑结果已经覆盖了绝大多数工作，剩余任务需要业务批准。|
|重复 CI 失败占用维护者，现有日志足以复现，历史上有足量人工诊断与真缺陷|先做失败分诊和证据整理。与当前重跑策略、人工整理的理想证据包分别比较，记录一次真修复的净人工时间及浪费的 CI 分钟。|生成证据包前后工程师采取同一动作、耗时相近；重跑主要掩盖真实回归，或实际等待来自评审。|
|候选 PR 产能上升，评审排队、重排或重复 CI 已可观察|先把当前队列、维护者容量、同批变更的测试基线连起来。产品交付物是已验证可合并的组合以及需人判断的例外。|队列等待主要由发布窗口或跨团队优先级决定；提前整理证据不能移动交付日期，或高风险漏放增加。|
|值班团队有可回放、已结案的事件和独立恢复信号|先测只读调查是否能指向可验证的证据，再由值班者核准允许动作；用受控演练验证恢复。|事故没有可还原的状态或恢复判据；高置信度结论经常选错资源，可执行动作仍需延期。|

**什么条件会改变首选。** 第一轮给 CI 分诊排了第一。跨仓迁移已经有来自 Airbnb、Google 和 Spotify 的具体现场，还可以用规则工具在相同的真实代码上建立起点。若近期有硬性迁移期限，它更容易回答“总共有多少工作、剩多少、谁能验收”；若组织没有这张清单，CI 分诊仍是合理入口。当前缺少你们团队的合格任务全集、等待分布和人力账，无法据公开资料替团队指定唯一第一名。[跨仓工程现场](https://airbnb.tech/infrastructure/accelerating-large-scale-test-migration-with-llms/) · [Google 迁移实践](https://research.google/blog/accelerating-code-migrations-with-ai/) · [Spotify 预先试跑与分批](https://engineering.atspotify.com/2023/05/fleet-management-at-spotify-part-3-fleet-wide-refactoring)

## 三项可以各自失败的产品假设

**一、让同类例外能被一次处理。** 在批量弃用旧 API 的工作里，平台先从编译、用例、owner 和消费者版本里生成逐仓清单。工程师给一个失败原因组示范一次处置，系统仅在相同前提成立的项目内重放。负责人看到覆盖的仓、仍缺的验证、已花的重试预算、放弃自动重试后谁接。对照是“已有规则＋维护者批处理”。如果仅把工程师从一张张 PR 的 review 移到审核一批模糊的推断，或者只有个别热门仓节约时间，停止扩面。Airbnb 的迁移长尾和本轮两种规则的覆盖反转说明为何要保留逐仓结果。

**二、让接管成为有范围的决定。** 在变更请求里保留目标、变更摘要、批准范围、有效期限和在途动作。暂停控制停止后续派发；已经写入的外部目标由接管者看到并判断是否补偿。审批只可授权当前对象，一次授权重发不能顺带授权下一步。对照包括引擎原生消息寻址、相同传输标识的重投，以及真正生成新消息标识的业务重复。若需要人为逐条检查才能防重复，人力成本会抵消自动化。由目标系统使用可重查的业务键、按内容版本条件写入，再把异常暴露给人。[LangGraph 中断语义](https://docs.langchain.com/oss/python/langgraph/interrupts) · [Temporal 重试语义](https://docs.temporal.io/encyclopedia/retry-policies)

**三、将 auto harness 接到独立的发布判定。** 可以让优化器改提示、工具、记忆策略甚至执行代码。保留旧版和固定的规则基线；用训练轨迹改版，用开发集选择少数候选，用按仓库或时间隔离的下一批任务验收。外层评估另记严重失败、总推理与 CI 开销和人工纠正，不让优化器改判分器。若总体均值上升但高风险分组出现不可接受的回归，继续用旧版；偶然胜过同轮其余候选的版本要过同一门槛。为每个候选明确谁能回滚及如何确认回滚后未完成动作。不同任务族最佳版本可能不同，是否值得分流要看维护成本。[Meta-Harness](https://arxiv.org/abs/2603.28052) · [AHE](https://arxiv.org/abs/2604.25850) · [AutoSaddler](https://arxiv.org/abs/2608.23041)

## 一次组织试点怎样算完

立项时由平台负责人、一个服务 owner 和实际接班人共同确定 eligible 的任务清单及剔除条件。分配前写明任务类型、风险、已有基线、质量底线、验证窗口和谁有权验收。按服务或团队分期开放，存在跨组学习时把相关任务放在同一组。单独保留没有尝试、自动失败、转人工、无终态和成功上线的记录。能独立验收的工作少时，先做质性回放，逐件写下控制失效处。

|看哪个数|分母和观察窗|由谁取证|
|---|---|---|
|交付周期与完成率|从全体合格任务的分配起算，到独立验收或统一截止。报告未完成比例，以及按任务类型的等待分布。|交付负责人从工单、CI、部署和服务信号对齐时间；对删失样本保留原始状态。|
|人工监督成本|记录构思、评审、等待中真正投入的分钟、纠错、接管和收尾，各角色合计。|抽样的工程师短记＋交叉核对。聊天通知间隔、PR 存在时间不能替代实际劳动。|
|质量与恢复|每项已交付任务看固定守护窗的回退、重复故障、漏过的严重问题；被过滤的结果另抽检。|由实际维护者或独立验收者盲核对，记录无权/无数据。|
|净投入|相同交付质量下计入人力、模型、CI、环境、平台研发和维护。同步报告成本总额、全部合格任务数、按期验收数。|平台和财务共同核成本，给试点期与可复用建设成本分别记账。|

按全体合格任务及按期验收任务分别报人工分钟和货币成本。折成金额时，将各角色节约的实际分钟乘含负担费率，先报告释放工时的估值，再扣除新增推理、CI、环境与平台摊销。现金节约另列实际减少的加班、外包或预算。若释放时间用于追加交付，按实际通过验收的增量记录，避免两次计益；已计入工时的返工不再扣。余项试出的增量要回填原始任务全集，不能按难例的单位收益外推全体。在同一批任务上只把等待作为周期指标；多人并行的等待量不能相加折算薪资。若质量底线满足且负担没有转嫁给其他 owner，再扩到第二个团队。若只提升 PR 产量，回看下游哪一步堆积。以上是建议的试点设计，此研究没有你们的内部生产数据或商业产品租户的实测结果。

做采购访谈时，可以同时问三个现有系统怎样交接这项工作。向工程效能负责人要一份定义明确的任务清单与分母；向 agent 平台负责人要本次执行真正使用的版本和批准记录；向服务 owner 要独立的完成判据与错误归属。前两项均有现成产品可接或可重用，第三项取决于本组织的真实消费者。[组织测量采购边界](eng-intel-vendors/result.md) · [生产版本与缓存](promotion-replay/result.md) · [事故消息与交接说明的证据](message-quality/result.md)
