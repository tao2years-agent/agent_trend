# 两种迁移规则在相同代码上能做到什么

**研究问题。** 在购买 agent 处理一批跨仓升级前，有多少工作用现成的语法规则就能完成？选取 Django、Requests、urllib3、Click、NetworkX、Pygments 共六个项目，各取两个预指定发行版本的官方 Python wheel。研究单位为 12 个版本快照、3,647 个打包 Python 文件，原始代码共 552 处字面字符串的 `.format()` 调用。两个版本可以共享代码，并非 3,647 个独立随机样本。实验只针对该类现代化改写；不把它推广为复杂 API 迁移效果。[预定范围](protocol.md) · [发布者下载地址与哈希](sources.json)

|同一批源文件|Ruff 0.15.0 / UP032|Flynt 1.0.6 非激进配置|
|---|---:|---:|
|调用净减少|355 / 552（64.3%）|395 / 552（71.6%）|
|被改动的文件|119|127|
|第二次运行仍变化的文件|0|0|
|Python 3.12 编译新增失败|0|0|
|手写的 12 个行为探针中实际改写|3|6|
|观察到返回值或记录的副作用轨迹变化|0|2|

**项目组合足以改变结论。** 单看 Pygments 2.19.1 的 142 处，Ruff 在该配置下不改，Flynt 减少 112 处。把这一版暂时移出，剩下 410 处的覆盖率顺序翻转：Ruff 为 355/410（86.6%），Flynt 为 283/410（69.0%）。在 Click 8.2.1 和 NetworkX 3.4.2 的打包源码中，两种工具都无目标可改。这些项目仍保留在项目级分母，否则批量发任务会凭空制造“工作量”。静态结果是调用数量净减少；它没有证明业务行为等价。[逐版本结果](summary.csv) · [逐文件记录](files.csv)

**同样的迁移，两种验证给出了不同答案。** 在分歧最大的 Pygments 2.19.1 上，取同一上游发行版的 examplefiles 与 snippets 黄金测试，保持期望 token 不动，分别运行原版及 Flynt 改写版。两边各运行 1,406 个测试，均通过。这支持本次样例覆盖到的词法输出。另在手写探针里，Flynt 对两个有副作用的表达式给出相同显示字符串，但改变了参数求值或格式化事件的先后；若验收只对最终字符串，两个差异都会漏掉。12 个探针是刻意构造的边界条件，2/12 不能用来估计项目缺陷率，也不能推断 Pygments 引入了实际缺陷。[上游测试结果](goldens.json) · [原始与转换后的探针观察](probes.json)

**一次实验配置错误。** 主运行把 Ruff 的目标统一设在 Python 3.8。Django 5.2.1 有两个源文件使用较新的 match 语法，Ruff 修复 99 处后返回非零。按适配该项目的 Python 3.10 重跑，退出码为 0，净减少仍为 99，仍修改 40 个文件。非零退出、发生文件变更与新语法损坏是不同信号。把失败简单重试可能重复工作，标成“完全未改”则会丢失已经生成的改动。[工具输出](run-log.json) · [目标版本敏感性](sensitivity.json)

**对采购的影响。** 有大规模迁移时先让规则工具扫一遍真实清单，分别列出本来无目标、可机械完成、需更强验证、确需逐仓判断四组。给 agent 的比较对象应是余下难例上的工程师与现成批变更工具；同时保留项目层“全部合格工作”的端到端分母。该实验没有调用模型，不能由它估计 agent 可再节约多少工时。
