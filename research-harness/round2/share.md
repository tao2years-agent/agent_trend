## 战略结论：停止复制 Code Agent，转做“组织级工作控制面”

**建议保留现有 Code Agent 作为可替换执行器，停止新增通用聊天入口、单仓 PR 生成器和基于跑分的简单路由。下一阶段只押一个楔子：跨仓迁移控制面。** 它接管的不是一次代码生成，而是一场有截止日、有依赖、有多位 owner、必须逐仓验收的工程行动。

35 个研发自动化产品的对照说明，单仓 issue→PR、代码审查、依赖更新、合并队列和事故调查都已有密集供给。Sourcegraph、Moderne、AWS Transform 已进入批量迁移；DX、Jellyfish、LinearB 已进入组织效能；LangSmith、Langfuse、Braintrust 等已覆盖评估与反馈。继续做一个“也能写代码”的产品，很难形成组织级壁垒。[Sourcegraph Batch Changes](https://sourcegraph.com/docs/batch_changes) · [Moderne](https://docs.moderne.io/) · [AWS Transform](https://docs.aws.amazon.com/transform/)

| 投资决定 | 具体处理 | 判断依据 |
|---|---|---|
| **停止** | 新通用 Coding Agent 壳、历史跑分路由、以 PR 数证明提效 | 5 个同模型历史系统在 500 题上的并集为 358，最佳单体为 265；按仓库历史成绩路由，20 次固定切分有 19 次输给单一强基线。|
| **复用** | 现有 Code Agent、规则迁移工具、CI、代码托管和工作流引擎 | 这些组件已能完成执行、重试、审批或采集。平台应把它们接入统一任务与证据协议。|
| **主攻** | 跨仓行动的任务图、例外队列、独立验收、版本化发布与全量对账 | 这部分跨越多个执行器、仓库和 owner，现有产品分别覆盖局部，还缺少可替换执行器的闭环控制面。|
| **暂缓** | 默认自动跳过 CI、用统一 AI 参与率做组织排名 | OpenStack 与 GitHub Actions 的同类跳过策略成本比相差约 6 倍；同一 DevLake 面板在两种数据库实现上可给出 40% 与 120%。|

这个选择有一个明确的反证条件：如果一项真实迁移的剩余工作主要卡在业务兼容决策或团队排期，平台再强也不会提前交付，应停止扩建执行层。

## 产品楔子：Migration Control Plane，不绑定某个 Agent

**首个用户是负责 API、框架或安全版本退役的平台负责人。首个成功标准是“在截止日前，所有合格消费者都有可核验终态”。** 产品输入是一张完整消费者清单、依赖关系、owner、截止日和验收规则；输出是已验收、阻塞、转人工、放弃、仍未决五类终态，以及每项的证据和责任人。

| 产品层 | MVP 必须交付什么 | 不应自己重造什么 |
|---|---|---|
| 工作图 | 仓库、依赖、批次、owner、权限、截止日；变更范围后可重新对账 | issue tracker、代码托管、通用编排引擎 |
| 执行器适配 | 同一任务可交给现有 recipe、Codex、Devin 或其他 Agent；保存实际版本与输入 | 新模型、编辑器、Agent 内核 |
| 独立验收 | 每仓使用 owner 认可的测试与业务判据；守护窗后才进入完成 | 让生成 Agent 给自己的结果打分 |
| 例外操作 | 按共同根因聚类；明确下一项必须由谁决定；支持换人和独立重试 | 对所有失败无限重跑、给所有 owner 发提醒 |
| 证据账本 | 尝试、人工分钟、外部写入、批准对象、最终状态可重放 | 只展示生成代码量或席位活跃度 |

采购或自研评审使用同一场景：给系统 12 个仓，两仓依赖前序包，一仓无权限，一仓测试失败；首轮开 PR 后更换 owner，再移除一仓。要求现场回答还剩什么、旧 PR 怎么处理、哪些动作已发生、谁能批准、用什么证据关闭。一次成功改完某个仓不计分。

选择迁移作为楔子的原因很现实：任务全集可枚举，机械基线足够强，难例会自然暴露组织协作问题，最终又能从运行系统验证。Airbnb 的 3,500 个测试文件迁移在四小时达到约 75%，四天达到 97%，最后约 3% 仍需人工一周收尾。产品价值集中在这条长尾，而不是前 75% 的代码生成。[Airbnb 工程记录](https://airbnb.tech/infrastructure/accelerating-large-scale-test-migration-with-llms/)

## 可上线的 Auto Harness：提议、验收、发布三权分离

**Auto harness 可以自动提出下一版，不能同时决定自己合格并把它推到生产。** 推荐架构包含两个闭环。工作闭环负责完成迁移；学习闭环从失败中提出新的提示、工具或策略。两个闭环通过不可变的任务版本和独立留出集连接。

| 决策点 | 自动系统负责 | 人只在这里介入 | 上线前必须制造的故障 |
|---|---|---|---|
| 任务接收 | 枚举消费者、解析依赖、提出批次 | 确认范围、业务例外和风险等级 | 中途新增/删除仓库、owner 更换 |
| 候选执行 | 选择执行器、运行工具、收集证据 | 对无法自动裁决的兼容决策拍板 | 权限丢失、部分成功、重复回调 |
| 独立验收 | 运行未暴露给提议者的判据，报告正负变化 | owner 对业务终点负责 | 测试全绿但业务判据失败 |
| 版本晋级 | 比较旧版与候选，保留回退路径 | 不参与提议的一方批准扩大范围 | 批准后内容变化、旧写覆盖新写 |
| 生产恢复 | 按操作键去重，核对消费者实际版本 | 严重副作用与补偿归属 | 写成功后丢回执、缓存未回滚 |

三项实证直接约束设计。第一，MLflow 3.18.0 中 production 从 v2 回到 v1 后，预热进程仍可默认读到 v2，版本号固定时模型配置也能原位变化。批准对象必须包含模板、模型、参数和发布代数，回滚要验到消费者。第二，Temporal 与 LangGraph 在“外部写入成功、调用者丢回执”时都会重试写入，业务目标必须接受操作唯一键。第三，ExplainBench 的历史补丁中，“单项复现测试通过”和“SWE-bench 整题解决”出现 210 个方向冲突的组合，交接卡要分别声明局部证据和整件状态。[MLflow Prompt Registry](https://mlflow.org/docs/latest/genai/prompt-registry/) · [Temporal 重试](https://docs.temporal.io/encyclopedia/retry-policies) · [ExplainBench](https://arxiv.org/abs/2607.26451)

人工介入的产品指标应是“这次打断是否改变了下一步决定”。24 小时未见终态或正式个人评审的 37,882 个公开 PR 中，16,502 个后来没有出现正式个人决定便合并或关闭。等待时间只能生成候选队列，不能直接决定通知谁。

## 90 天立项：用一次真实迁移决定继续、收缩或停止

**成立一个小型跨职能小队，只做一项真实迁移。平台负责人拥有任务全集，服务 owner 拥有验收，评估负责人拥有留出集，执行器团队只提供适配。** 90 天后只决定是否扩大控制面，不承诺通用自治平台。

| 阶段 | 必须完成的产物 | 评审问题 |
|---|---|---|
| 0–30 天：冻结事实 | 全部消费者、依赖簇、owner、现有规则基线、验收与守护窗；历史任务只用于发现失败模式 | 任务全集是否可信，主要瓶颈是否真在工程执行？ |
| 31–60 天：影子运行 | recipe＋人工基线与 Agent 流程同题对照；记录全部角色主动分钟、等待、失败聚类、未完成和外部写入 | 新系统减少的是劳动，还是把负担转给服务 owner？ |
| 61–90 天：受控放量 | 只扩大已在另一仓/另一周留出集通过的策略；演练断线、换人、审批后变化和回滚 | 严重回归能否阻止晋级，回滚是否真的到达消费者？ |

建议在启动前签字的决策门槛如下。这些是立项门槛，不是公开研究得出的行业平均值。

- 全部合格任务必须进入五类终态，禁止静默消失；按任务等权和按依赖簇等权同时报告。
- 守护窗后的验收率至少不低于现有流程，所有角色主动劳动分钟应出现预先约定的实质下降；等待时间单列，不能折算成人力节约。
- 任一严重外部写入或不可回滚问题立即暂停放量；零事故只表示本轮未观察到，不能证明可靠性。
- 候选 harness 必须在未见任务上、相同预算下击败旧版；开发集上涨、留出不变时只保留失败分类，不晋级。
- 现金收益只计算实际减少的加班、外包或预算；释放工时和新增交付分别报告，避免重复计益。

**90 天后的三个答案应该非常清楚。** 若难例能够跨仓复用、人工分钟下降且验收不退化，继续建设迁移控制面；若收益只来自某个执行器，把能力留在执行器适配层；若主要阻塞是业务排期和兼容决策，停止平台扩建，把证据账本交给现有项目管理流程。
