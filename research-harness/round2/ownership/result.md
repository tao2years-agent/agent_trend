# 出现例外时，该把 PR 交给谁？

**以首位留下正式决定的个人账户作为可核验代理指标，仅靠仓库历史，月初冻结的“推荐最常评审的人”在 15,203 个可标记 PR 中首选命中 4,827 个（31.75%），前三命中 7,310 个（48.08%）。** 让系统在每次预测前吸收当时已经发生的正式决定，首选升至 42.84%，前三升至 61.51%。即便如此仍有许多 PR 无人可从同仓历史推出。历史上最常评审的账号也并非可无限触达：冻结规则在最忙的一天将 250 次首选落到同一人身上。[完整指标](results.json) · [独立 SQL 检查](sql-check.json)

这些结果支持将 reviewer 建议做成有人确认的候选名单，并在历史不足时提供人工接管入口。真正的例外工单、人员在线状态、被邀约的目标、授权责任人和实际接班均未观测；本实验在公开 agent PR **创建时**预测后续首位可见正式决定者，未向任何人发送通知，无法据此估计缩短了多少等待时间。

## 创建时能知道哪些事实

使用 AIDev v5 作者发布的热门公开仓库子集，固定提交 b8dc67df…。全量 PR 表 361,296 项、review 表 541,831 行。创建于 2026-02-01 至 03-01 前的 67,327 个 PR、8,700 个仓库全部进入留出，未按是否成功或是否有人回复筛选。30 天内 15,203 项（22.58%）有首个可见个人 APPROVED 或 CHANGES_REQUESTED，另 52,124 项没有这个标签。后者仍参与覆盖统计和分配预算，不能推断无人看过。7 日内可标记 14,056 项。30 天窗口全部在作者 03-31 快照内；v5 曾修复早期分页缺陷，迟于窗口的补抓记录被时间条件排除。[预注册协议](protocol.md) · [固定数据卡](../empirical/raw/README.upstream.md) · [完整分母](coverage.json)

最小输入是 PR 的仓库和创建时刻，以及已发生的同仓正式决定。使用作者标注的 User、正式 review 状态和已知机器人排除规则；人的身份不能独立验证。训练按同一人参与的**不同 PR 个数**计频，连续复审同一 PR 不会加频；最近时间可随新的正式决定刷新。预测目标按 submitted_at、review id 排序，30 天内首个决定同一时刻由多账户产生的 PR 数为 0。仓和个人信息只用于本机计算，输出为汇总数。[运行器](study.py) · [来源索引](sources.json) · [取列哈希](../empirical/raw/ranges.json)

本次另外读取 timeline 的 assignee 列检查“已经叫过谁”。属于留出 PR 的 56,954 个 review_requested 事件中该列**全部为空**，其中 1,135 事件与 PR 创建时间相同。actor 是执行请求的账户，无法替代被请求者。作者数据目录中的 pr_commit_details 为 12.45 GB，来自整个 PR 提交历史，未证实文件在创建时已经出现；文件级表对部分非常大的 PR 还有缺口。本次没有把事后路径、合并、审查文本、未来该 PR 的互动拿来排序。[请求字段可用性核验](request-field-audit.json) · [数据文件目录](../empirical/raw/tree.json)

## 两种部署方式和五条规则

**月初冻结**将训练截止固定在 02-01 00:00 UTC。实际纳入 68,394 个个人正式事件，覆盖 44,633 个 PR、6,101 个仓和 10,894 个个人账户，最后可用事件在 01-31 23:29:15 UTC。**逐案滚动**从同一历史开始，仅当事件提交时间严格早于当前 PR 创建时才加入。它可以利用本月先前其他 PR 已实际发生的决定；同一时刻不加入。先对全量 PR 排序、记账并产出预测，再单独构造标签。[逐时点检查](study.py) · [边界](coverage.json)

仓内高频按不同历史 PR 计数，仓内最近按最后一次决定排序，仓内首位高频只数各 PR 的首个正式决定者。可弃权的版本只收录在该仓至少评过两个不同 PR 的人。限额版本在此基础上，每人每天跨仓最多作为首选三次，遇到已满的账号继续往名单后方找。Top3 只是可见候选，假想触达预算仅扣首位。无历史不跨仓猜。预算对同日所有 PR 都记账，包括事后没有可见标签的 PR；预算和 2 次历史门槛均为预设情景，未经组织实践定标。

## 哪些请求不适合硬派

冻结时有 **6,070 个留出仓、30,851 个 PR** 没有可辨认的同仓正式历史。15,203 个有标签 PR 中，3,437 个来自完全冷启动仓，另 2,601 个虽然仓内有历史，但是最终首位决定者没有出现在该仓的历史正式名单。即使能将所有已有候选都完美排序，也最多覆盖 9,165/15,203（60.28%）的首位决定者。滚动时这个可达上限增加到 11,544/15,203（75.93%）。在看不到组织成员、CODEOWNERS 或值班轮换的情况下，直接把仓内未见过的人排进候选缺少依据。[可达性统计](coverage.json) · [SQL 复核](sql-check.json)

将分母收窄到至少有指定数量已经被个人正式评过的历史 PR，可检验“只在成熟仓推荐”的取舍。下表均为仓内高频，选择条件在每个时点依据当时历史判断，所以滚动条件下一仓在月内可以从冷变热。

| 历史条件 | 满足条件的全部 PR | 其中可标记 PR | 有标签仓 | 条件内 Top1 / Top3 |
|---|---:|---:|---:|---:|
| 冻结，至少 1 项 | 36,476 | 11,766 | 1,648 | 41.02% / 62.13% |
| 冻结，至少 3 项 | 29,604 | 10,257 | 1,101 | 40.08% / 63.23% |
| 冻结，至少 10 项 | 19,297 | 7,889 | 546 | 39.84% / 64.47% |

要求更多历史通常缩小覆盖。冻结条件从至少 1 项改为至少 10 项时，条件内 Top3 从 62.13% 升至 64.47%，Top1 却从 41.02% 降至 39.84%。换成 7 日首位标签，冻结高频在 14,056 个可标记 PR 的 Top1 / Top3 为 32.53% / 49.08%，滚动高频为 43.97% / 62.84%。需要注意的是，一个请求量较大的仓可能有多个合格维护者，命中首位留痕者这一指标会把其他合理候选都当作错。[全部门槛、时间窗、覆盖和集中度](results.json)

## 到可落地的接管契约还缺什么

首选推荐若只求命中，冻结规则会把 18.95% 的首推集中于前十个账号；最忙个人单日 250 次。加入历史门槛和每日三次的模拟上限后，前十占比降到 3.79%，峰值按设定降到 3，已标记 PR 的首选命中也降到 20.61%。不能据此推断之前真实有人收到 250 次通知，或者三条是合理容量。可先按“列候选、由人确认、饱和则转轮值”的模式记录结果，再判断提高覆盖与减少骚扰该如何权衡。

若要在组织内部验证**是否缩短等待且没有把工作转嫁给同一小群人**，需要直接记录例外发生时刻、当时可用且有授权的值班名单、真实请求目标与接受/拒绝/无人响应、首个可负责处置的动作、解决时刻及后续转派。以合格例外任务为分母，在同仓、相近值班和风险条件下对照候选名单与原有分派流程，统计等待、重派、漏响应及每人负荷。公开数据没有反事实分派结果、未被邀请者的可用性或人员耗时，当前数字仅支持路由与容量的离线可行性判断。
