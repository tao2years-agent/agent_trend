# 如果 harness 能改写自己，谁来决定新版本可以上岗？

这里讨论的 auto harness 有两个执行者：内层 agent 解决研发任务，外层优化器改动内层可用的提示、工具、中间件或上下文管理代码。外层面对的目标是让下一批任务做得更好。要判断某产品是否做到了这一点，可以问它到底改了什么、谁看过哪些任务的答案、哪个环境独立验收，以及局部进步能否掩盖其他任务的退化。

**由哪些证据改变了产品建议。** 做一个按失败轨迹改 prompt 的演示已经有许多参照。更值得试的是选版与退回：给失败任务及其相邻的成功任务同时建样本，限制可改动的组件，配对比较基线与候选，展示“修好哪几例，又弄坏哪几例”。把同一改动放到下一周或另一个仓库的未见样本；单独否决严重回归。每次晋级由不参与提议的一方执行。若当前纯规则基线很强，要报告新方案相对强基线的增量以及筛掉的失败候选成本。单次跑分与设定比较条件的能力，是两种不同的商品。

**最小立项试验。** 任务选用一种有独立验收的内部迁移；冻结执行模型与工具版本。让人工维护的 recipe、只能改提示的优化器、能改提示及验证动作的优化器，在相同预算下各跑。历史期只用于发现原因，开发集用于晋级；另仓/另周的任务在最后解封。业务指标是每个通过独立验收的迁移消耗的人时和算力、严重回归及弃单。审批检查器和生产权限在本试验中由平台 owner 管理。若训练期上涨、留出不变或退化，只保留失败分类和可回放证据，不推广自动修改。

**核查。** 六篇均核过正文指定页及首页题名。一次搜索所得的候选编号 2610.00598 对应的实际 PDF 是天体物理论文，已按题名不匹配剔除，不充当负面证据。原始文档及内容指纹随专题保留。
