# 给下一次研发平台评审的决定

**保留 code agent 作为能干活的执行器。给平台新增的职责是管理一项跨人、跨仓工作的去向，并让每次变更能被外部验收。** 这两项职责有现成客户，也都有现成替代品：服务负责人现在用清单、CI、工单和人际协作做它们。判断值不值得单独建设，要先量出那套现有流程中确实存在的成本。

### 一个可以拿去做演示的例子

假设产品线规定十周后退出旧 API，12 个目标仓分属三个小组。这是采购验收脚本，不是已经发生的客户案例。

1. **开始。** 平台按冻结清单为每个消费者列明当前依赖、兼容范围、独立环境中能跑的最小请求、谁有权确认下线。现有依赖更新机器人和批量规则先跑一次，把已经能自动处理的部分留下作对照。[依赖组合实跑](compat/result.md) · [已有规则覆盖](migration/result.md)
2. **第一次跑完。** 九个仓生成 PR，两个因共享依赖失败，一个无权限。让服务负责人处理这一类共同失败，保留每个仓的具体证据；前一仓批准上线不能顺带给第二仓授权。一个仓临时退出范围时，停掉未来派发并列出已经产生的分支、部署与待撤销动作。[工作产品同题对照](workflows/result.md) · [恢复与副作用](handoff/result.md)
3. **交接。** 值班人换班之后只收到一张可行动的卡：哪些目标已可验证、哪个依赖未准备好、已经对目标系统写了什么、哪种重试已耗完预算、需要他裁定的具体选择。以真正操作方的回执对上工单、产物摘要和批准范围。记录工程师的决策与实际分钟；通知已读与尝试次数都不足以代表成功。[交付事件和规范](interoperability/result.md) · [预测接班人的限制](ownership/result.md)
4. **让经验进入下个版本。** 把本次同类失败做成候选改动，把其他仓与以后发生的失败留给独立验收。旧版、现有规则和新版在同一费用上限内运行；任一严重回归可以否决候选。最后逐仓检查真实消费者是否已经迁出，别在最后一条 PR 合并时提前结案。[两个优化器的选择逻辑](optimizersrc/result.md) · [验收器的反例](gates/result.md)

### 哪些证据足以改变路线

- **继续做跨仓工作。** 在现有规则之后仍有足够多的可复用难例，真实维护者能按时验收，跨仓重复处理、接班和返工的合计人时减少，质量守护期没有出现超出预设边界的问题。若时间主要花在等待消费者同意升级，转做责任归属、兼容证明和排期协调。若原有规则已处理主要负担，保留集成即可。
- **让 CI 先给建议。** 需同时抽查被推迟和实际派发的请求。工程负责人先为“错过一次本可转绿”与“继续跑一次”取成本区间；上下界足以改变最优动作时，保留人的覆盖与补跑入口。在灰度阶段先识别数据是否真在决策时可见。[OpenStack 时钟审计](ci-availability/result.md) · [GitHub 的不同分母](ci-cross/result.md)
- **给 human on the loop 设明确终点。** 有些授权必须事前批准，其他任务可事后抽查、按例外叫人。除可见评审事件外，计入有人打开任务后重新找信息的时间，以及无人能接手而取消的工作。把“有人愿意接”与“系统能预测历史上谁接”分别验证。[接班与容量](ownership/result.md) · [提醒时机](supervision/result.md)
- **扩大自动调优。** 按预设预算、独立未见任务和严重错误阈值比较。对未尝试、模型超时、验收缺失和用户放弃全部保留。若只在开发集改善或收益依赖删去无断言的任务，让旧版继续服务。[三种评估工具的本地探针](evalops/result.md) · [路由留出](pairing/result.md)

**批准下一笔投入所需的最小材料。** 一份客户真实任务清单，一份现有流程的强基线，一名能确定最终验收的 owner，以及计入失败、人工接管和等待的全量结果。先决定哪项负担确实值得平台接手，再决定自建哪些共用能力、集成哪些现有产品。
