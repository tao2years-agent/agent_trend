# 从 Code Agent 到组织级研发自动化

**决策建议｜把第一笔投入放在已有 CI 失败后的诊断与接管。** 平台可以接手归集证据、受限复现和准备修复；让有权限的人裁决例外，让独立测试与上线观测决定何时结束。下一个投资点是把接管失败编译成可回放的 harness 测试。两者共享事件和证据，能分别检验价值。先试一个团队的一类失败，得到团队净耗时和质量数据后再扩到跨仓升级。

## 组织到底购买什么

考虑一次支付库升级。Agent 在 A 仓改完 API，单仓 CI 全绿；B 服务尚运行旧版；平台团队收到第二个相似的失败工单；审批人在群里回复过“可以”。谁能认定这项工作完成？模型可以提出兼容补丁，CI 只能报告它实际运行过的用例，服务 owner 才能确认旧版消费者仍需兼容。部署之后，线上错误率还要跟相同流量的基线比较。这个情境是设计推演；真正要消除的是每次故障都由人重新找工单、版本、负责人和验收证据的成本。[P12] [P18] [D08] [I24]

上期组织上下文研究给出了提交前补关键验证、阻塞时找对确认人、跨仓查询消费者版本三个候选。本期把它们接到可操作的研发状态上：知道某个测试存在后必须记录是否运行，找到 owner 后需要记录其决定覆盖哪个版本，知道消费者版本后要能推迟发布或批准兼容窗口。三件事任意一件只有检索命中，工作都可能还卡在原处。

|关心的结果|工作单位|观察终点|容易得出的错误结论|
|---|---|---|---|
|执行器能否解题|给定环境下的一道可验收任务|独立检查通过，日志可复核|拿历史公开题的成绩代表交付速度|
|工作流能否代办|一个 issue、告警或升级请求及所有后续尝试|产物提交、未解例外路由或明确放弃|把 agent 退出、PR 打开算作任务完成|
|人能否有效监督|一次异常、拒绝、撤销或超时|有权的人理解原因且能停止/接替|把通知已发送或按钮被点过算作有效监督|
|组织能否更快交付|同期所有符合条件的任务，含失败和放弃|业务验收、发布后守护期、总投入|把合并数、席位活跃、采纳率做收益分母|

### 产业前沿的三种现场

**Stripe 做了一件很具体的事：规定一轮失败有多少次机会消耗整套 CI。** 蓝图先以确定性代码运行 lint 和 push，把需要搜索或修复的部分留给 agent。第一次远端失败先应用可用的自动修复，剩余失败才交给 agent 再尝试一次，第二次提交并运行 CI 后交回人工。团队自报每周超过 1,300 个这类人工审查后合并的 PR。这证明它在 Stripe 的基础设施上运行到了规模；缺少同期全体符合任务的分母、评审时间和返工数据，无法把 PR 数解释为节省工时。可移植的是“重试有上限并附带交接”，上限值应由本队列的 CI 成本和成功分布决定。[I02] [P03]

**OpenAI 的路线从让 agent 看见结果，走到了部署后重新开判断。** 先是每个 worktree 都能启动应用并读取隔离的指标、日志与浏览器状态；随后 Symphony 用工单状态替代逐个照看会话，一项工作可以关联多个 PR，或只交付调查。11 月 18 日公布的 Performance Factory 更进一步，让另一轮调查在部署后回到原任务，检查延迟等指标是否恢复。前后来自同一供应方，不作为三个独立企业的交叉证明；它们给出了一个阶段差异：控制对象从会话变成工单，完成条件从“提出修复”变成“观察到服务恢复”。[I01] [I17] [F01] [I16]

**GitHub 与 Cursor 给出了两种分发路径。** GitHub Agentic Workflows 在 10 月 28 日 GA，将 Markdown 工作流编译为 Actions YAML，复用现有 runner、策略和受限写入。Copilot cloud agent 的仓库自动化另有身份与审批约束，不能把两者的权限假定相同。Cursor 3 月把外部事件接入云沙箱，5 月支持多仓和无仓任务。由此推断，单做“看到通知就叫一个 agent”缺少差异化；企业会继续遇到的决策是由谁授权、重复事件如何处理、多仓何时算完成、什么时候停掉没有产出的自动化。[I04] [I05] [I06] [I07] [I18] [F02]

## 从市场能力到产品设计

### 1. Auto harness 应能改进自己的规则，也要证明这次改进有效

工程上有两条循环。第一条处理一次任务：获取需求与版本，准备环境，运行有限动作，收集外部验证，由人裁决或交付。第二条处理一种失败：把失败轨迹与人的纠正关联，从历史样本里留出未见过的一组，在同一模型与工具条件下比较旧、新策略。通过后才把新规则发布给部分任务，有退化就恢复旧策略。很多案例展示了第一条的局部能力。第二条比较难，因为谁标注失败、哪些旧数据失效、规则版本如何关联历史结果，直接改变你得到的结论。[I14] [I16] [O04] [O05]

同一失败的四种修法成本不同。若模块压根无法导入，优先修镜像和依赖清单；若不知道验证哪个行为，补业务验收样例；若云端运行已经结束但父会话没有收到结果，修任务完成事件传递；若每次模型调用都重读无关日志，再试上下文裁剪。RISE 的轨迹研究甚至在评测平台找到了错误，北大与字节跳动等合作的 AgentDiet 则证明有些上下文可减。两者合起来说明，先定位失败层能避免把环境故障一律归结为提示词不够好。[P01] [P05] [E08]

**落地对象。** 每个任务绑定输入修订、策略版本、代码修订、环境标识、尝试号、证据和终止原因。模型可建议新 recipe，不能自行通过有外部写入权的规则发布。把“搭建支持环境”的时间单独核算：如果为一个低频任务维护一套镜像和验证数据比人工修复更贵，应该关掉这条自动化。发布或停止由负责该工作流的团队决定，不能只看模型调用方的成本。[E03] [D01] [P19]

### 2. Human on the loop 需要成功接管的证据

**人的工作分布在三个时刻。** 运行前，流程 owner 设定允许的写入对象、影响半径、时间/费用与回滚条件。运行中，过期批准、不可判定的测试、需求冲突、超预算或外部影响扩大才触发接管。运行后，维护者抽样判断误放、误拦和绕过门禁的情况。单次需要判断业务语义的改动仍采用 human-in-the-loop 的事前批准；低风险且可回滚的批量工作可以用 human-on-the-loop 的运行监督。分类取决于任务，而非给整个 agent 一个永久自治级别。[I07] [E01] [D08] [I22]

|人的动作|界面必须回答的问题|可检验的失败|
|---|---|---|
|审阅或拒绝|这次批准覆盖哪个 commit、计划摘要、目标环境、到期时间？|批准之后又 push，在旧界面继续执行；应让旧批准失效或明确触发重新确认。[D08] [D11]|
|暂停或撤销|新任务是否停止领取？已派发动作到哪一步？谁已确认取消？|任务进程已退出但外部写入仍排队。要分别验证禁止新写、在途动作和收尾。[D02] [D03]|
|接替诊断|最后确认的好状态、已排除的解释、最小复现和下一项区分性检查是什么？|接管者必须完整重跑或等原作者解释；用交接后首次正确动作的时间测量。[P06] [I16]|
|恢复任务|从哪个节点继续？之前提交的写入能否去重？|LangGraph 本机实验中，0.2.71 和 1.2.24 两版的同进程内存检查点上，同节点中断前的计数操作在恢复后累计两次，已完成前驱节点计数仍为一次。[E10]|
|延后裁决|owner 不在线怎么办？何时退回给原请求人？|无人确认的高风险任务在超时后被默认放行；真实演练应测试节假日与队列拥堵。[O01] [O08]|

Endsley 与 Kiris 的经典导航实验表明，自动化出错时，操作者对情境的了解与接管后的决策时间有关。它没有研究研发团队。本期能从专业开发者调试现场得到的对应证据是，人要重建系统解释，往往需要知道尝试过什么和为何排除。产品上值得测试的具体差异是，在同一条故障前，一组只收到告警和日志，另一组拿到原始信号、已排除假设、下一个检查以及可执行的暂停动作；比较谁更快作出正确处置。[I22] [P06]

### 3. 验证控制着自动化的上限

最昂贵的错觉是所有步骤都成功，而任务实际未完成。k6 代码显示在没有聚合样本的特定路径上一轮阈值判断可被跳过并返回通过；Argo Rollouts 为无结论、错误及失败保留不同的判定；Promptfoo 的总体阈值可能让某一项失败仍取得足够高的总分。统一展示一个绿勾会损失这些语义。平台应让结果带上测到了什么、覆盖多少、是否存在观察空窗及检验器版本。这里的 k6 无样本路径是源码证据，实际 CLI 对照测试覆盖的是有样本的通过与失败。[O10] [D05] [O06]

对一个候选修复，最低要求可以是“旧版本复现失败，新版本同样环境通过，再运行独立回归”。对于数据迁移还需要双向兼容或回放；对用户体验还要真实交互；对于形式化了的少量属性，检查器可独立核验证明。对照 AutoRocq 的工作可以看到，证明被接受仅保证命题推导，命题是否写对仍需领域判断。有些变更暂时没有廉价、独立的判据，这就是将其留给人或先投资测试的产品依据。[P02] [P08] [P16] [I24]

**不同终点产生不同的胜负。** USEagent 在混合任务集做消融，去掉 ExecuteTests 后，一类子任务的成绩从 8.7% 到零，同表另一类保持 49.6%。这反对用一个榜单决定是否为所有任务多跑一次工具。工业评审研究也给出另一个方向的证据：自动评论常被标为已解决，但三项目合并观察到平均 PR 关闭时间从 5 小时 52 分变为 8 小时 20 分。评审活动增加、问题修复、等待减少三个效果需要单独测量。[P20] [P11]

### 4. 组织产出需要完整分母

要回答“提效了吗”，先冻结试点期间所有符合条件的工作，包括被拒绝、未分派、人工做完、被放弃和到期仍进行中的任务。每个任务记录是否指派自动化、人工实际投入、评审与值班时间、机器费用、墙钟历时、验收结果与观察到的复发。保留同一 issue 关联多个 PR 或零 PR 的可能。验证器、模型、策略和任务来源都要有版本。面板中的缺失显示为未知，有资源成本但没关联到结果的记录应单列。[P18] [O02] [O11]

**三个表面冲突的证据实际回答了三个问题。** Stripe 报自己能交付多少机器编写且人工审查的 PR。METR 早期随机试验问的是原本熟悉仓库的 16 人在 246 个已选任务上用时如何，允许 AI 后实现时间估计增加 19%。METR 在 2026 年又解释为何新招募及并行工作让同一实验设计变得不可靠。11 月，METR 在获得 Anthropic 部分内部数据和访谈权限后开展的研究则观察特定 AI 研发组织的模型能力进展速率；公开报告提示显著加速的可能，也明确关键证据被删节且归因不确定。吞吐、单任务人时、特定组织研发进展速率不能在同一张百分比排行榜相减。[I02] [I08] [I09] [I21]

**一个能检查成本转移的算例。** 假设某月有 100 个合格失败任务，基线每项人工 40 分钟。新流程每项节省调查 16 分钟，却分别给审查和例外处理增加 6 和 5 分钟，另花 600 分钟维护回放环境。月净变化为 100 × (16 − 6 − 5) − 600 = −100 人分钟；机器使用费尚未计入。这是假设演算。采纳量、单次生成速度很可能都上升，团队仍可能亏损。单独报告工程师人时、墙钟和货币，在财务与团队约定折算前保持各自单位。[I23] [O11]

## 试哪里，怎么知道该停

下列阈值是建议预注册的业务判据，均未在贵司验证。试点先过安全与可恢复性检查，再看方向和区间；样本不足时保留“不确定”。比较以任务为单位，在同一服务和故障类型内分层；同一人同时处理多个任务时不要把并行等待重复计作人时。

|优先度与负责人|试点及对照|主要结果与反证|停止或升级条件|
|---|---|---|---|
|第一，平台 CI 团队 + 两个服务 owner|回放最近约 40 个符合条件的 CI 失败。A 为既有日志/重跑；B 加确定性聚类和历史匹配；C 在 B 上加受限 agent 复现与证据包。盲审判断下一步。|首次正确定位、接管人主动分钟、错认代码故障、重跑费。按仓库和原因分层，保留无法复现项。|若 C 无法比 B 减少人工，部署 B 即可。若错误自动写入或关键证据缺失，停写并继续只读。通过后进真实影子流量。[P01] [P03] [P08]|
|第二，agent 平台 + 质量负责人|从人工接管记录抽样，同一模型、数据集、工具版本对旧新 harness 做配对回放；留出跨周新样本。用标注队列给覆盖不足的失败补标签。|独立验收率、严重失败数、单次合格交付成本、接管者能否解释结果。固定数据与模型，再单因素比较。|任一严重项回退就不推广；只在训练样本上获益时退回采样。新策略小流量投放后仍观察复发。[O04] [O05] [O06] [I16]|
|第三，发布工程 + 值班团队|同一历史版本变更回放跨仓依赖、生产版本与 canary 窗口。A 为当前提醒，B 在 PR 旁给版本、关键检查和影响者，C 再按可撤销策略派单。|未知组合、误放、误拦、接替耗时、等待真正授权人时间、回滚成功。刻意包含空指标与旧批准。|任何不可恢复误放都拦截扩大流量。若目录找不到 owner 或生产版本不可查，先补数据源。[D05] [D08] [O01] [I24]|
|探索，研发效能团队|在有义务维护的多团队迁移上比较“发更多 PR”和“按评审人容量发放任务”。用等待时间与进行中工作量调并发。|已验收的服务迁移数、排队 p90、每位维护者被中断次数、弃单、未部署补丁和尾部服务风险。|若增加并发只增加待审库存，降低派发速率；若瓶颈实为发布窗口，停止优化生成阶段。[I17] [P07] [P11]|

### 前 90 天的决策安排

**第 1–2 周**，项目负责人锁定一个有可靠回放环境、独立 owner 和高频失败的服务，对照组沿用现有 CI。记录不参加的原因，以免只纳入容易题。先抽十例让人手工组装理想证据包；如果理想证据包也改变不了接管动作，暂停 agent 封装，转查真正的等待点。[P06] [I09]

**第 3–6 周**，为历史任务做盲审，加入预先设计的坏样本：过期审批、重复事件、空遥测、同一分支的新提交、没有 owner 的服务。先测能否辨别这些错误，再比较独立验收和净投入。复核给出失败类型、具体证据和下一次应该改变的一个环节，避免多项同时改动后无法归因。[D08] [E10] [O10] [P01]

**第 7–12 周**，选择低影响任务做小流量、可撤回试点。观察期内保持原发布策略，建立主动人时、尾部等待、复发和成本的周度记录。同步复核哪些新工单是 agent 自己创建的，避免用自创需求填高吞吐。月末可选扩大、保留只读、降级到脚本或停用四种决策。若源码或产品版本跨越重大变化，先重跑相同失败集再做决定。[I17] [D06] [O07] [I24]

## 市场选择与未决问题

**现成工具可承接的部分**包括模型执行、日程触发、runner、渐进式发布、基础遥测与标注。已有企业版平台应先试其现成对应能力，按相同的任务回放对照。值得自建的候选是公司独有的验收条件、历史失败资产、审批关系，以及跨工具串起的交接体验。每一部分都可独立被现有工具替换。流程团队负责规则，服务 owner 负责验收与例外，平台团队负责执行、隔离、回放及可恢复性；组织层只消费汇总结果，个人排名不是试点交付物。[I18] [O01] [O04] [P12]

**最可能推翻这条路线的三个事实**是现有 CI 已能低成本给出同样的诊断；多数等待来自没有决策权的排队，技术证据改变不了队列；平台补齐环境和回放的维护成本大于减少的调查人时。每一种分别对应确定性基线、按责任人做的分层队列分析、含维护和失败尝试的成本账。没有这些证据前，可以决定启动试点，不能承诺年度 ROI。
