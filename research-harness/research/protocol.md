# 研究协议 · 2026-11-20 上海
对象为研发平台负责人、研发效能与产品团队。决策问题是既有 code agent 之后，哪类调度、验证、接管与组织反馈值得投资。以截止日以前的公开材料为界；旧论文追溯机制起源。目的抽样，不估算市占率或全球覆盖率。
## 执行顺序
1. 读取上期组织上下文专题和 checkpoint。继承“补关键验证、找确认人、查跨仓契约”三个现场；本期增加执行策略、交付、组织效果归因。原专题不重复计数。
2. 从执行层、交付层、组织平台三个层各取 11 个可独立辨识的项目。有源码证据才进入核心机制样本；同一厂商不同项目分列，项目数量不等于厂商数量。另开商业前沿及内部工程实践样本，明确开放范围。
3. 每个样本用同一组问题追踪：输入和触发、工作对象、状态变化、验证、人的权限与时机、失败或不可恢复的边界、组织运行成本。固定代码与变更证据分开，历史事件不能证明首次引入。同一生态的关联单独披露。
4. 论文沿研究对象检索。核对 CCF 会议名录及分轨，研究轨、行业轨、期刊优先报告与 workshop 分列。检索 2025–26 的工程现场、人机交互、失效分析及测试，也保留早期可复核基线。记录候选与排除理由；能读正文时补充方法与有效性威胁。课题组按关联的公开产物入选。
5. 首轮提炼机制，次轮主动寻找反证：无人 PR 能否当有效交付、绿测能否当验收、队列与同一责任人的判断是否成为瓶颈。第三轮把结论翻译成可否证的内部试点；未开展的实验不得写成收益。
6. 生成深报、Wiki、来源与离线洞察。审计字段、证据路径、日期、去重和跨输出计数；检查浏览器桌面、窄屏和离线交互。
## 证据口径
代码说明该修订上的实现，版本记录说明该次变更，产品文档是供应方声明；案例报告是该团队在其环境中的经验。论文只在其抽样、测量与干预边界内支持结论。各层证据互补，不能把“读取源码”写成“运行成功”，也不能用市场宣传给产品排全局名次。
