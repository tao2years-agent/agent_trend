## 建议先改哪一步

**把一次 CI 失败交回给人时，让接管者能立即做出下一步判断。** 平台先收集失败日志、执行环境和上次成功版本，区分“代码真坏了”“环境不一致”“测试偶发”“证据不足”。只给可复现且可回滚的情况一次受限修复机会。把复现条件、尝试结果、仍未知的事项和恢复入口放回原工单。[I02] [P01] [P08]

这是对原有 code agent 投入的延伸：既有执行器继续写补丁，平台新增的价值是知道何时该让它动、怎样证明结果、出了意外由谁接。第一轮同时保留纯规则方案；如规则已经解决大部分等待，就把它作为交付结果。

## 三种自动化现场如何判定完成

|现场|他们如何结束一次工作|对产品决策意味着什么|
|---|---|---|
|Stripe Minions|确定性 lint 和 push 搭配 agent 修复；第二轮 CI 后交回人工，合并前由人审。[I02]|重试预算属于工作流。每周逾千个 PR 是部署规模的证据，不能直接换算人力。|
|OpenAI Performance Factory|告警触发诊断，工程师审查修复，部署后另有 agent 回原任务核对性能是否回基线。[I16]|把生产恢复纳入完成条件，能暴露“代码已合并、用户仍受影响”的落差。|
|GitLab Duo / Cognition Devin|GitLab 的定时自动化可查看运行和失败原因；Devin Bots 把需人处理的 PR、权限与决定收进 Needs you。[M04] [M02]|一个视图回答自动化是否跑通，另一个回答谁还需要做什么。采购时用同一个失败工单走完两种路径。|

## 把接管做成一种能力

给审查人一个可以操作的对象：这次变更的提交与计划、影响服务、还有哪条证据缺失、暂停后哪些动作仍在途。把“允许这个人发布”“这个人批准过这次变更”“批准后产物未再变化”分别验证。Atlantis 的计划校验与审查并不天然绑定；本机 LangGraph 实验也显示恢复会重新执行当前节点中断前的副作用。[D08] [E10]

适合自动处理的是结果可独立检验、可回滚、影响范围有限的任务。需求含糊、跨团队承诺、生产信号缺失时，交给能承担结果的人。评估监督做得好不好，可以让另一名维护者接手，观察他是否能在不重跑整个调查的情况下做出正确决定。[P06] [I07] [I24]

## 提效最容易看错在哪里

|看起来的胜利|应同时观察|
|---|---|
|评审机器人建议很多，也有人点了已解决|三个工业项目中 73.8% 的自动评论标记已解决，同一研究的平均 PR 关闭时间却从 5 小时 52 分变为 8 小时 20 分。前后比较不能单独归因，足以要求同时测评审等待。[P11]|
|一个团队 AI 采用率较高|不同产品分别统计生成动作、开发者日活、带标记的提交或代码行。计量单位不同，不能直接换算成已交付 PR。先核对定义和未入样的人，再看已验收交付、返工与团队总投入。[B01] [B02] [B03] [B04] [B05]|
|公开榜单上升，内部试点理应更快|历史基准有污染和测试过度指定的风险；熟悉仓库的开发者在一项早期随机试验中用了更多时间，后续招募又遇到明显选择偏差。把两者都当成设计内部对照的理由。[I08] [I09] [I12]|

## 哪些创新值得投

**先做失败案例的回放库。** 维护者纠正一次诊断后，保存前提、输入修订、错误输出与独立验收条件。在相同模型、工具与成本预算下比较新旧 harness，留一批新工单不给调优者看。Tessl 的同任务有无 skill 对照和 Phoenix 的数据集版本管理都可复用。只有新策略在未见案例上仍少占用人工，才逐步扩大部署。[F03] [O05] [I16]

**再试按评审容量派工。** Symphony 已能从工单持续派发，Graphite 能并行验证相依的 PR。若同一维护组积压，调高 agent 并发可能只把等待从编写移到审查。可在相同发布窗口比较“固定并发”和“按在途审查量限流”，观察最终完成的服务迁移数和尾部等待。[F01] [M06] [P11]

## 三项研究如何改变验收设计

|研究|对产品的实际影响|
|---|---|
|新加坡管理大学 RISE 分析 8 个 agent 的 3,977 条求解轨迹和 3,931 份测试日志，还发现了评测平台自身的错误。[P01]|失败看板应能分别指向环境、执行器、补丁或评测器，避免一遇到红灯就让模型继续改代码。|
|NUS 等团队移除 ExecuteTests 做消融，一类任务从 8.7% 降到 0%，同一表另一类仍为 49.6%。[P20]|按任务类型选工具。把全平台平均分换成分类型通过率，再决定是否承担每次运行的成本。|
|ReproFlake 给 1,115 个不稳定测试配套环境、通过与失败日志，以及复现和修复校验脚本。[P08]|把“运行过”提升为“别人能复现和复查”。无法复现的任务同样计入总分母。|


## 第一个试点

**基线 A** 沿用现有 CI。**基线 B** 增加无模型的历史匹配与确定性分类。**实验 C** 在 B 上加入受限 agent 复现和交接材料。先用约 40 个历史失败做方向判断，再上只读影子流量；这个数是试点建议，无法替代统计功效分析。

- **工程服务 owner** 盲审下一步处置是否正确，计入未能复现和被放弃的任务。
- **平台团队** 记录主动调查、审查与维护人时，另列 CI 等待和机器成本。
- **发布负责人** 预先规定停止条件。出现过期批准仍写入、严重误放、无法撤销，立即停写。C 若不能超过 B，保留简单规则。
- **试点负责人** 只把得到人纠正、并能变成独立验收的案例放入下一轮回放；用跨周留出样本检验新策略，保留退回旧策略的路径。[O05] [D08] [I16]

**立项判断。** 此刻值得立项的是对一个确定瓶颈做低成本对照。能否扩为组织平台，取决于它是否减少整个团队的投入、守住发布质量，并在新任务和新版本上继续有效。
