# Research Protocol

## 研究问题

1. AI Agent 办公产品如何从“个人助手/单体 CLI”演进为多人、团队和组织协作系统？
2. WorkBuddy、千问办公、ChatGPT/Codex、Claude/Claude Code 及重要参照产品分别采用什么产品结构？
3. 如果要设计支持跨团队、跨组织协作的 Agent 办公产品，产品与技术上必须解决哪些问题？

## 证据架构

| 层 | 目录 | 约定 |
|---|---|---|
| 不可变来源 | `raw/` | 按来源 ID 与抓取日期保存原始响应和 metadata；刷新不得覆盖旧快照 |
| 来源与覆盖 | `corpus/` | 稳定来源 ID、筛查状态、产品矩阵、证据声明 |
| 机制实体 | `features/` | 去重后的协作机制、设计含义和未验证问题 |
| 编译 Wiki | `wiki/` | 产品页、机制页、跨产品综合判断与索引 |
| 输出 | `outputs/` | 管理层/产品/技术报告与离线 HTML |
| 研究状态 | `state/` | checkpoint、决策、问题、追加式日志 |
| 脚本 | `scripts/` | 抓取、生成、校验 |

## 来源优先级

1. 产品官方文档、管理指南、协议规范、发布记录。
2. 厂商官方产品页、博客和安全白皮书。
3. 标准组织、政府机构与原始论文。
4. 媒体和社区材料仅用于找线索，不单独支撑关键能力断言。

## 证据等级

- `official_fact`：官方材料直接说明的事实。
- `research_inference`：由多个事实推导的研究判断，必须标出推断。
- `planning_proposal`：面向产品规划或技术架构的建议，不冒充竞品事实。
- `open_question`：公开材料不足、版本/地域/套餐不明或需运行时实验。

## 覆盖状态

- `captured`：已固化原始页面或保存失败元数据。
- `screened`：已判断与研究问题的相关性。
- `deep_reviewed`：已定位到具体机制、边界或管理控制。
- `runtime_verified`：已用真实账号或环境验证。未执行实验时不得使用本状态。

## 时间纪律

- 当前文档只证明当前能力，不倒推出首次发布时间。
- 发布日期、文档更新时间和本次抓取时间分开记录。
- “已发布”“灰度”“Beta/Preview”“仅文档宣称”分开表达。

## 完成门槛

- 核心产品均有官方来源、产品页和横向矩阵。
- 关键结论能解析到官方 URL 与本地 raw 快照，抓取失败需显式记录。
- 同租户协作、跨应用协作、跨组织协作不得混用。
- 产品事实、研究推断、规划建议明确区分。
- Wiki 链接、来源 ID、离线 HTML 生成与渲染冒烟检查通过。
