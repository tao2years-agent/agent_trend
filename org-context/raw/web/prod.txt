L39: Claude Tag is a new way for teams to work with Claude.
L40: We’re starting on Slack, which Claude can join as a team member. Grant Claude access to selected channels, and connect it to whichever tools, data—and even codebases—you choose. Then, anyone in the channel can tag @Claude in, and delegate tasks to it while they focus on other work. Claude builds context by remembering relevant information from the channels it’s in, and can plan out tasks to complete in the future.
L41: We see Claude Tag as the beginning of an evolution of Claude Code: it makes the model even more proactive, and it works better with a full team. Tagging @Claude is now one of the main ways we get things done at Anthropic. Today, 65% of our product team’s code is created by our internal version of Claude Tag. The same pattern is now spreading well beyond engineering—we’re tagging Claude to chase down product metrics and data, work through support tickets, or even help find the root cause of tricky bugs.
L42: 【10†Image: Video thumbnail†assets.claude.com】
L43: 
L44: We’re launching 【11†Claude Tag on Slack†www.claude.com】, since it’s a natural home for collaborative work between teams and AI, and where much of Anthropic’s day-to-day work already happens. It’s available today in beta for Claude Enterprise and Team customers. Our goal is to expand where it’s available more widely, so that teams can tag @Claude in the many other places they work.
L45: ### Working with @Claude
L46: 
L47: If you’ve worked with Claude Code or Cowork before, Claude Tag will feel familiar. Tag @Claude with a request in simple terms and it’ll break its task down into stages and then work through them in turn, using the tools it has access to. Once it’s done, it’ll respond in a Slack thread with what it’s created.
L48: 
L49: But tagging Claude comes with a few new advantages:
L50: @Claude is multiplayer. Within a given Slack channel, there’s one Claude that interacts with everyone. This means that anyone can see what it’s working on, and can pick up the conversation from where the last person left off. This makes tagging Claude very different from working within a single chat or for a single task—it’s much more like interacting collaboratively with a teammate.
L51: @Claude learns over time. As Claude follows along with its channel, it builds more context about the work. This means that users don’t need to explain things to it from scratch over and over again. And Claude can even automatically learn from other Slack channels and data sources, if it’s granted permission. (It doesn’t report from private channels.) This gives it the tacit knowledge necessary for it to provide the best possible work.
L52: @Claude takes initiative. If “ambient” behavior is enabled, Claude will proactively keep you updated about whatever it thinks you might need to know. It’ll flag relevant information from across the channels it’s in and the tools it’s connected to, and follow up on threads or tasks that have gone quiet without being resolved.
L53: @Claude works asynchronously. Set Claude a task, and you can focus on your other priorities while it works. It can also schedule tasks for itself, pursuing a project autonomously over hours or days. We’ve found this particularly helpful at Anthropic: we now spend much more of our time delegating tasks to many Claudes in parallel.
L54: 
L55: You can also send Claude direct messages: it’ll respond privately, using the personal tools and connectors you’ve set up.
L56: ### Getting started
L57: 
L58: We’ve designed Claude Tag with teams and organizations in mind: @Claude’s access to sensitive data and task-specific tools can be very tightly controlled.
L59: To get up and running, system administrators specify which tools and information the model should have access to, in which channels. Think of it as creating separate Claude identities for different uses: everything, including its memories, will stay scoped to the channels defined by the administrators. For example, a model set up for sales work won’t pass on memories to one set up for engineering; nor will it give engineers access to any sales data or tools.
L60: More information about provisioning access is 【12†available here†claude.com】.
L61: Once permissions are set, everyone can begin tagging right away. Administrators can set limits for token spend (both for the organization and for individual channels), and can view a log of everything that @Claude has done, along with who requested each task.
L62: 
L63: If you’re a Claude Enterprise or Team customer, you have access to Claude Tag in beta starting today. To get started, 【13†visit here†claude.ai】 and follow these four steps:
L64:   1. Pair Claude Tag with your Slack workspace
L65:   2. Give Claude access to your tools
L66:   3. Set a limit on your organization’s monthly spend
L67:   4. Test Claude in a private channel to confirm it works.
L68: 
L69: Claude Tag replaces the existing 【14†Claude in Slack†support.claude.com】 app. To migrate, administrators can opt in within 30 days. We’re issuing an introductory 【15†launch credit†support.claude.com】 to eligible Enterprise and Team organizations so that the whole company can try it out.
L70: Claude Tag works with Opus 4.8. You can 【16†read our docs†www.claude.com】 and 【11†product page†www.claude.com】.

L96: # Project-Level Memory for Coder Agents in 2.39
L97: 
L98: ### What's new in 2.39
L99: 
L100: Give Coder Agents your conventions, context, and skills once, at the project or organization level, and every chat builds on them. Platform teams can also trace any workspace connection end to end and see every editor their developers use.
L101: ### Coder Agents: Shared context and admin controls
L102: 
L103: Set conventions, skills, and model access once instead of repeating them in every chat or organization.
L104:   * Organization skills and instructions: Admins publish 【38†skills】 and 【39†instructions】 once per organization, can limit them to specific groups, and every change is recorded in the 【40†audit log】.
L105:   * Manage model access in Terraform: The coderd Terraform provider can now set which users and groups can use each Coder Agents model, and configure Claude Platform for AWS. 【41†View the provider release†github.com】.
L106:   * Projects: Group related chats in 【42†projects】 with shared memory, instructions, and 【43†skills】, so each new chat builds on the last one.
L107: 【44†Image†www.datocms-assets.com】
L108: ### Script ordering for templates
L109: 
L110: Template authors can set the order `coder_script` resources run with the new 【45†`coder_script_order`】 data source, so dependencies install before an IDE or AI coding agent starts. It's in beta, opt-in, and requires Coder Terraform provider v2.20.0 or later. 【46†Learn more in our documentation】.
L111: ### More improvements
L112:   * Trace any workspace connection end to end: VS Code, JetBrains Toolbox, `coder ssh` and the web terminal tag each session with one ID across client, server and agent logs, so platform teams can find why a connection dropped in a single SIEM search, without debug flags. 【47†Learn how to trace workspace connections】.
L113:   * See every editor your developers use: Template Insights, connection logs, and Prometheus now track each editor by name, including VS Code forks such as Cursor. See the 【48†connection logs】 and 【49†Prometheus】 docs.
L114:   * VS Code extension 1.17: Developers now see a warning when a startup script fails or times out. Version 1.17.0 also includes a 【50†security fix†github.com】, so we recommend updating. Learn more in our 【51†documentation】.
L115: ### Security updates
L116: 
L117: We've recently patched several disclosed vulnerabilities. Check our 【52†security advisories†github.com】, and 【53†watch for new releases†github.com】 on GitHub to hear about patches first. For updates on vulnerabilities we have patched, visit the 【54†Coder Trust Center†trust.coder.com】.

L35: Agents should understand more than your codebase—they should understand how your team works. Your preferences, repository conventions, skills, and custom instructions guide how changes should be made, while code in related repositories can show how the pieces fit together. Without that context, agents spend time rediscovering knowledge and can miss your team’s conventions.
L36: GitHub intelligence is the context and learning layer sourced from the graph of GitHub data. It makes this data useful to agents, helping them remember how you work, keep that guidance current, and find the code and development history relevant to the next task. The goal is for agents to build on what you and your team already know, rather than treating every session as a fresh start.
L37: That is the advantage of building where your team’s work already lives. A repository memory can capture why an edge case matters and which test covers it. GitHub intelligence allows agents to use that context, with controls over what they can access.
L38: 
L39: Three capabilities bring this into your workflow:
L40: 
L41:   * Memory carries knowledge between sessions
L42:   * Dreaming keeps the context current
L43:   * Code search reaches beyond your checkout.
L44: 
L45: Availability and settings vary by capability.
L46: ### 【9†Memory: Pick up where you left off】
L47: 
L48: 【13†GitHub Copilot Memory†docs.github.com】 is now generally available on paid Copilot plans. Copilot can remember personal preferences and repository conventions across sessions and clients. Memories can be created in the Copilot app, Copilot CLI, VS Code, Copilot cloud agent, Copilot code review, Slack, Teams, and GitHub Mobile.
L49: You can tell Copilot, `Remember to start my pull request descriptions with a TL;DR`, and it can reuse that preference across Copilot experiences. Repository memories can capture the right test command or how your team expects Copilot to check its work, so you spend less time repeating guidance in each session. Copilot sessions autonomously generate and curate memories, learning from every interaction.
L50: Among the Copilot CLI sessions reviewed during the public preview where the agent used memory, 93% showed better adherence to developer preferences and 42% showed more efficient workflows attributed to the memories included in the session context.
L51: 
L52: You can interact with memories in the Copilot app, Copilot CLI, and VS Code, or manage personal memories in your Copilot settings, where you can 【14†view or delete saved preferences†github.com】.
L53: ### 【10†Dreaming: Continuous context improvement】
L54: 
L55: Copilot dreaming, now in public preview, reflects on past work to improve future agentic sessions.
L56: 
L57: Three dream types are currently available:
L58:   * Personal memory curation customizes Copilot to your personal preferences by updating memories based on your agent conversations.
L59:   * Repository customization manages repository-scoped memories and proposes updates and improvements to existing skills and custom instruction files.
L60:   * Code review customization turns recurring accepted code-review feedback into guidance for Copilot code review.
L61: Dreaming can add, update, and remove personal and repository memories. Changes to checked-in skills and instructions are proposed in pull requests for your team to review.
L62: 
L63: Dreaming is opt-in.
L64:   * Individual subscribers: Enable personal curation in your Copilot settings and repository dreams in each repository’s settings. See 【15†personal and repository setup†docs.github.com】.
L65:   * Organizations and enterprises: Administrators 【16†enable dreaming through Copilot policies†docs.github.com】. Enterprise administrators can delegate that choice to organization administrators. Repository dreams cover the repositories allowed by Copilot Memory’s repository access settings. Users must also enable personal dreaming in their own Copilot settings.
L66: Dream runs consume AI credits. See the 【17†dreaming documentation for prerequisites, setup, and costs†docs.github.com】.
L67: ### 【11†Code Search: Reach beyond your checkout】
L68: Software projects rarely live in a single repository. 【18†GitHub code search†docs.github.com】 helps Copilot find relevant code, configuration, schemas, and documentation across related projects and dependencies without needing a local clone. Copilot can search for exact text and symbols, match patterns with regular expressions, and narrow results by repository, path, or language.
L69: 【19†Semantic search†docs.github.com】 can also find code by what it does, such as retrying a failed payment, even when you don’t know the file, function name, or repository it lives in.
L70: For example, you’re fixing failed payments, but retry behavior spans a payments service, a shared library, and background workers. Use `/research` to ask Copilot, `How do these components retry failed charges, and where could retries overlap?` Copilot can inspect implementations and callers across those repositories to help you understand how the system fits together before changing it.
L71:
