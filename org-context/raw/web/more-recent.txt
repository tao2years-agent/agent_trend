L41: Claude Tag lets you add Claude to a Slack channel, where it works alongside your team. Claude responds when you @-mention it, or proactively when it thinks it can be helpful.
L42: 
L43: Before, Claude only saw one message at a time, so it made decisions to act proactively based on what was in front of it, but not the wider context of what was around it.
L44: Now, Claude uses context from across the channel, as well as its memory and the standing instructions you have given it, to determine when to contribute to the conversation.
L45: 
L46: As a result, Claude is now roughly 30% better at determining when, and when not, to proactively respond.
L47: 
L48: This update comes at no additional cost today. While holding more context does increase Claude Tag’s usage, the additional context Claude Tag holds does not count toward usage or spend limits on any plan.
L49: ## From passive responder to active participant
L50: 
L51: Previously a lightweight classifier decided when Claude should act. It looked at each new message on its own and made one yes-or-no call.
L52: 
L53: For example, here are two engineers chasing the same bug from opposite ends. Neither has a free hour to run it down, and neither message asks for anything.
L54: 
L55: 【13†Image†assets.claude.com】Priya has a theory. Devon has the evidence. Neither message is for Claude, and neither asks for anything.
L56: Read one at a time, neither message is for Claude, so the classifier correctly does nothing, twice. Read together, there's an obvious piece of work sitting there. One engineer has a theory, the other has the evidence for it, and nobody has time to check.
L57: 
L58: With the classifier removed, Claude uses context across the channel to make one of four moves:
L59:   * Reply inline, when the answer is short, verifiable, and something the channel doesn't already know.
L60:   * Start deeper work in a thread, when a message deserves real time.
L61:   * Route the message to work it has in flight, when it adds to a workstream Claude already has open.
L62:   * Say nothing, when nothing is called for.
L63: Here's the same conversation with Claude Tag using additional context. Claude picks the second move, even without being @-mentioned. It sees Priya's hypothesis and Devon's evidence, opens a thread with the investigation already running, and pulls both engineers in. It acts within the boundaries of the permissions, tools, and scope you have configured.
L64: 
L65: 【14†Image†assets.claude.com】
L66: 
L67: Same thread, two minutes later. Claude reads the two messages together and starts the work. No @-mention.
L68: The conversations aren't walled off from each other. So when Devon posts an update, it lands in the right workstream. When two investigations turn out to be the same bug, that connection gets made.
L69: 
L70: 【15†Image†assets.claude.com】
L71: 
L72: Claude now looks at all messages to understand the full context of the channel, to more accurately determine if it should participate in a conversation unprompted.
L73: ## How Claude decides when not to speak
L74: 
L75: An annoying agent is worse than an unhelpful one. We built Claude Tag to speak up only when it's useful, and in most channels, on most messages, that means saying nothing.
L76: 
L77: We do this by grading Claude’s channel-by-channel choices against a rubric based on principles like how useful the comment is, how confident Claude is in the response, and whether there is a person better suited to respond.
L78: Claude also knows when to stop paying attention, similar to how people navigate Slack. It follows a few channels closely while paying less attention to others until someone tags it in. In a channel where, message after message, Claude keeps concluding it has nothing to add, it goes to sleep. A @-mention wakes it instantly.
L79: 
L80: You can also steer its response behavior in plain language: "Never respond here unless someone tags you," or "Feel free to jump in on anything about the deploy pipeline."
L81: And if you'd rather Claude only spoke in a channel when someone tags it, 【16†any member can switch ‘Respond automatically’ off】.
L82: ## The first reply is faster
L83: 
L84: The additional context also allows Claude to respond more quickly. It acknowledges you in seconds instead of operating silently while it starts up. The work itself takes as long as it always did; what's gone is the silent first minute when you couldn't tell whether it heard you.
L85: ## Live today
L86: 
L87: This update is now available across Claude Tag, available for Claude Teams and Enterprise customers. You can get started 【17†here†claude.ai】. Claude now acts as a more effective collaborator, one that can follow the conversation, decide for itself when to act, and when to stay out of the way.

L161: # Access verification
L162: 
L163: Use Document lookup to check whether Glean has indexed a document and whether a teammate can access it.
L164: ## Look up a document【97†​】
L165: 
L166:   1. Navigate to 【98†Admin console → Content management → Document lookup†app.glean.com】.
L167:   2. Enter the document URL or ID in Document URL.
L168:   3. To check access for a teammate, select them in User (optional).
L169:   4. Click Check document.
L170: 
L171: After Glean finds the document, review these fields:
L172:   * Last crawled: When Glean last scanned the document for changes
L173:   * Last indexed: When Glean last added those changes to search
L174:   * Document visibility on Glean: Whether the document is visible or hidden in Glean
L175:   * Document access: Whether the selected teammate can access the document
L176: 
L177: note
L178: 
L179: Glean assigns a unique document ID when it successfully crawls a document.
L180: ### Find a document ID【99†​】
L181: 
L182: If you don't know the document URL or ID, or the URL returns an error:
L183: 
L184:   1. Below Document URL, click using the document ID.
L185:   2. Select the option that describes your access to the document.
L186:   3. If you can access the document, search by title or URL and click Add ID next to the correct result. If you can't access it, ask a teammate with access to find the document ID.
L187:   4. Click Check document.
L188: 
L189: ## Troubleshoot missing or stale documents【100†​】
L190: ### Document not found in lookup【101†​】
L191: 
L192: If the document URL or ID returns no results, possible causes include:
L193: 
L194:   * The document was recently created or approved in the source application and the next crawl cycle has not run yet.
L195:   * The connector's permissions prevent Glean from accessing the document.
L196:   * The URL or ID does not match the format Glean expects for that connector.
L197: To resolve this, confirm that the document is accessible in the source application, then check your connector's crawl schedule on the 【102†Connector refresh rates】 page. If the document should have been crawled already, go to Admin console → Platform → Connectors, select the connector, and review its Status and Last crawled timestamp.
L198: ### Stale "Last crawled" or "Last indexed" timestamps【103†​】
L199: 
L200: If the Last crawled or Last indexed timestamps are older than expected, the connector may be experiencing crawl delays. Common causes include API rate limits, large corpus sizes, or source application outages.
L201: Go to Admin console → Platform → Connectors and review Crawl rate and Change rate for the connector. If the connector appears healthy but the document is still stale, contact 【104†Glean Support†support.glean.com】 to request a targeted recrawl.

L73: # Repo Wiki
L74: 
L75: Repo Wiki automatically generates structured documentation for your project and continuously tracks changes in code and documentation. When you query knowledge points, code explanations, or add feature enhancements during development, Repo Wiki deeply analyzes the project structure and code implementation. Combining Repo Wiki with context information, it provides more accurate and detailed answers and documentation support, giving the agent a deeper understanding of the codebase.

L91: 【43†​】
L92: 
L93: Repo Wiki Generation
L94: 
L95: The Wiki in your repository is not static—it stays synchronized with your code. The Wiki updates in three key scenarios. Understanding when and why it triggers helps you keep the Wiki updated in real-time.
L96:   1. Initial Wiki Generation When you open a project for the first time, no Wiki exists by default. You can generate it from scratch with one click.
L97:   2. Code Changes Detected After the initial generation, the system continuously monitors code changes. If you modify content already recorded by the Wiki (e.g., function signatures, class definitions, API endpoints), the system detects the inconsistency between the current code and the existing Wiki. You can click Update to regenerate only the affected parts.
L98:   3. Git Directory Sync If you directly edit Markdown files in the Git directory, the system detects inconsistencies between the Git content and the Wiki. You can click Sync to synchronize the Git changes and update the Wiki.
L99:   4. Generation Limits
L100:      * A maximum of 10,000 files per project. If your project contains more than 10,000 files, it is recommended to exclude non-essential paths in Qoder IDE Settings → Codebase Indexing → Index Exclusions.
L101:      * Only supports Git repositories with at least one commit.
L102: ##
L103: 
L104: 【44†​】
L105: 
L106: Intervening in Wiki Generation
L107: 
L108: Repo Wiki is not a "generate once and read-only" artifact. You can guide the direction through a configuration file before generation, or modify it anytime after generation. Every knowledge revision made by the team is recognized by the system as new cognitive deposits—it won't be overwritten by the next automatic update, but instead reverse-synced to the corresponding knowledge cards—truly embedding human judgment into knowledge assets.

L63: # Using the Real-time Search API
L64: 
L65: The API formerly known as the Data Access API
L66: 
L67: Are you looking for the Data Access API? You found it! The Data Access API has evolved into the Real-time Search API. Read more about it 【32†here】.
L68: The Real-time Search (RTS) API allows apps to access Slack data through a secure search interface. This approach enables third-party applications to retrieve relevant Slack data without storing customer information on external servers. Supplying this data as context to a large language model (LLM) helps ensure more relevant and accurate responses to user queries. Read on to discover how to employ this API exclusively in your 【33†app using AI features】.
L69: The Real-time Search API is designed for real-time data retrieval and is intended to be used in response to user interactions, either within Slack or from a third-party system that has an active Slack connection. It performs searches across all channels the user has access to within their Slack workspace and returns an array of messages and files relevant to the search query.
L70: 
L71: Make it org-ready
L72: Consider making your app that uses the RTS API an 【34†org-ready】 app. Doing so allows you to manage a single user token and send a single request to query every workspace the user and app have access to.
L73: ## API overview【35†​】
L74: 
L75: The Real-time Search API can be used in two scenarios:
L76: 
L77:   * When a user interacts with an 【36†AI-enabled app】 within the Slack client. With this method, a bot or user token can be used.
L78:   * When a user interacts with a third-party service that has an active Slack connection outside of the Slack client. With this method, a user token is required. Details on user authentication and API flows are outlined below.
L79: Using the Real-time Search API, your app performs the search on behalf of the authenticated user, ensuring that only content the user has access to is returned.
L80: 
L81: No unlisted distributed apps allowed
L82: 
L83: The RTS API is available for directory-published apps and internal apps only.
L84: ### User authentication【37†​】
L85: 
L86: To use the Real-time Search API to fetch private conversation data or to use it outside the Slack client, a user token is required. To obtain this token, your application must ask each user to go through the 【38†OAuth authorization flow】. To initiate this, direct the user to your Slack app's installation URL, which can be found in the Manage Distribution section of the app settings page. Upon successful authorization, your app will receive the user's `xoxp-` user token.
L87: ### Required Scopes【39†​】
L88: 
L89: Your app must contain at least the `search:read.public` scope and can optionally contain any of the scopes following that in this list. Each provides various levels of access. Include all of them for a wider base from which to search.
L90: Scope  | Description  | Token Type Allowed
L91: --- | --- | ---
L92: 【40†`search:read.public`】  | Read access to all public channel messages  | Bot, User
L93: 【41†`search:read.private`】  | Read access to all private channel messages  | User
L94: 【42†`search:read.mpim`】  | Read access to all multi-person direct messages  | User
L95: 【43†`search:read.im`】  | Read access to all direct messages  | User
L96: 【44†`search:read.files`】  | Read access to all files  | Bot, User
L97: 【45†`search:read.users`】  | Read access to a workspace's users  | Bot, User
L98: The `search:read.public` scope allows searching for data in public channels within the workspace(s) where the app is installed AND the searching user is a member. The searching user need not be a member of the public channels, just of the workspace, for the channels to be included in the search results.
L99: Including any one of the `search:read.private`, `search:read.mpim`, and `search:read.im` scopes allows users to consent to those scopes within the Slack client. Users can choose to grant access to their private channels. They can only grant that access if the app has been installed with the corresponding scope. For example, if an admin installs the app with the `search:read.public` and `search:read.im` scopes, users will be able to consent to the IM scope, but not private/MPIM.
L100: The `search:read.files` scope grants access to search for files, but it needs to be combined with channel-type scopes to determine where those files can be search. For example,
L101: 
L102:   * `search:read.files` + `search:read.public` grants access to public files
L103:   * `search:read.files` + `search:read.private` grants access to public and private files
L104: 
L105: Having the `search:read.files` scope lets you search for files, but if you want to download the file content, you also need the `files:read` scope.
L106: Additionally, the following scopes are useful to have in an AI-enabled app too:
L107: 
L108: Scope  | Description
L109: --- | ---
L110: 【46†`im:history`】  | View messages and other content in DMs the app has been added to
L111: 【47†`chat:write`】  | Write access to post messages channels and conversations
L112: 
L113: To add these scopes, go to your 【48†app settings†api.slack.com】, select your app, then:
L114: 
L115:   1. Go to the OAuth & Permissions section in the navigation sidebar
L116:   2. Scroll down to the Scopes section
L117:   3. Add the scopes listed above
